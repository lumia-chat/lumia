# Spike: event-log write path

Date: 2026-11-01. Code: `apps/instance`, `mix lumia.spike.events`. Answers the first question in architecture section 18: does the per-channel `seq` design (section 8.1) hold up, and does hash partitioning by channel prune as intended?

## Setup

- Apple Silicon laptop, Postgres 18.4 (Postgres.app), Elixir 1.20.4 / OTP 29, Ecto 3.14.2, Postgrex 0.22.4, pool size 10.
- One transaction per write: lock and increment the channel row, insert `events`, insert `event_payloads` (1 KB jsonb body), insert `commands`, insert `messages`, commit.
- 50 concurrent writers, 15 seconds per scenario, 2 seconds warmup, via Benchee `parallel: 50`.
- Two scenarios: **hot**, every writer on one channel; **spread**, writers randomly across 100 channels.

Laptop numbers. They establish shape and order of magnitude, not production capacity.

## Results

| Scenario | Writes/s | p50 | p95 | p99 | max |
|---|---|---|---|---|---|
| Spread, 100 channels | 10,360 | 4.76 ms | 5.50 ms | 6.05 ms | 60.6 ms |
| Hot, 1 channel | 2,853 | 16.8 ms | 22.9 ms | 27.2 ms | 42.4 ms |

Hot-channel latency is queueing on the row lock, not slow transactions: 50 writers serialized on one row at roughly 0.35 ms per commit gives the observed 2.8k/s and the observed p50 of about 50 × 0.35 ms. A real channel never has 50 concurrent writers, so the floor under the send budget (section 17) for a single channel is the commit time, under 1 ms here.

## Partition pruning

All three queries prune to a single partition or use the intended index:

| Query | Plan | Buffers | Time |
|---|---|---|---|
| Sync: `channel_id = $1 AND seq > $2 LIMIT 200` | Index scan on one `events_pN` primary key | 157 | 0.08 ms |
| Idempotency: `channel_id = $1 AND command_id = $2` | Index scan on one `commands_pN` primary key | 3 | 0.01 ms |
| Reconciliation: `last_seq_at >= $1` | Index scan on `channels_last_seq_at_index` | 129 | 0.09 ms |

## Finding: the channel row must stay HOT

The first run indexed `last_seq_at` at microsecond precision. Every write changed an indexed column, so no update could be a HOT update, and each write added an index entry and a dead heap tuple. After 15 seconds the reconciliation query touched **43,178 buffers to return 100 rows** (4.35 ms), and would have kept growing until vacuum caught up.

Fix, now in the migration and `Lumia.Events`:

- `channels.last_seq_at` is stored at **second** granularity. Writes within the same second do not change the indexed value, so the update is HOT.
- `channels` has `fillfactor = 70` so pages have room for HOT chains.
- `changed_since/1` is inclusive (`>=`) and truncates its argument, so a channel written in the same second as the last tick is returned again. Spurious nudges are allowed by section 8.2; missed ones are not.

Same workload after the fix: **129 buffers, 0.085 ms.**

The general rule this leaves behind: **never put a per-write-changing column of a hot row in an index.** It applies to any future "last activity" column.
