# Spike: the native store and MLS engine on the web, unchanged

Date: 2026-11-02. Question from the step 6 grill (plan): can the Rust core own the store on the web, so the SQLite store, the MLS key-value store, the DM engine and the identity flows built in steps 3 to 5 run in a browser worker without a port to JavaScript?

## Setup

- `rusqlite` 0.41 builds for `wasm32-unknown-unknown` through its `ffi-sqlite-wasm-rs` feature; `sqlite-wasm-rs` 0.6 compiles `sqlite3.c` with the `cc` crate for the wasm target, and `sqlite-wasm-vfs` 0.3 provides the `opfs-sahpool` VFS (the OPFS synchronous access-handle pool ported from the official SQLite WASM build).
- The spike crate copied `lumia-client/src/sqlite.rs` as is, with two changes: the clock (`js_sys::Date::now` where native uses `SystemTime`, which traps on this target) and an `open_on_vfs` constructor. It depends on `lumia-core` unchanged, OpenMLS included.
- Built with `wasm-bindgen` 0.2.130 for `--target web`, run inside a dedicated `Worker` (the synchronous access handles exist only in workers), driven by Playwright through a static server.
- One trap on macOS: the `cc` crate archives wasm objects with Apple's `ar`, which produces an empty archive and a link failure with a handful of undefined `sqlite3_*` symbols. `AR_wasm32_unknown_unknown` must point at `llvm-ar` from the toolchain's `llvm-tools` component. The build is otherwise ordinary.

## What ran

Round 1 on a fresh origin: install the VFS, open `lumia.sqlite` on it, apply 200 channel events through `Store::apply` (events, materialized messages and the cursor in one transaction), then an MLS round trip where a memory-backed "native" device creates a group, adds the web device from a key package whose private material went into the store, and sends an application message; the web device joins from the welcome and decrypts inside one store savepoint.

Round 2 after a page reload: open the same file, read the messages and cursor back, `Conversation::load` the group, read a meta value.

## Results

Playwright 1.64 with persistent browser contexts (WebKit disables OPFS in ephemeral ones), Apple M-series laptop, release build, no `wasm-opt`:

| Step | Chromium | WebKit |
|---|---|---|
| VFS install | 8 to 55 ms first time, 7 to 13 ms on reload | 7 ms, 6 ms on reload |
| Store open with schema | 37 to 48 ms first time, 10 to 13 ms on reload | 17 ms, 4 ms on reload |
| Apply 200 events in one transaction | 9 to 15 ms | 7 ms |
| MLS: key package, create, add, welcome (setup) | 22 to 23 ms | 8 ms |
| MLS: join from welcome and decrypt one message, in a store savepoint | 9 to 11 ms | 3 ms |
| Reload: 200 messages and the cursor back from OPFS | 2 to 3 ms | 1 ms |
| Reload: group state back from OPFS | epoch 1, 2 members, as left | same |

The `.wasm` is 4.4 MB before `wasm-opt`, with SQLite, OpenMLS and the Rust crypto providers inside; the brotli size and `wasm-opt` savings are to be measured when the real crate is built. WebKitGTK, the Linux engine, is not on this machine; it has had OPFS synchronous access handles since 2.40 and is covered by the Linux CI build of the Tauri shell.

## Decisions it settles

- **Rust owns the store on the web.** The store, the MLS key-value store and the engine run unchanged; the web build differs from native in the clock and the VFS. `lumia-client` gets a wasm target with its transport behind target gates, and `lumia-wasm` grows from the bare session to the client surface.
- **The transport goes the same way.** Every piece the native gateway loop needs has a wasm backend: `reqwest` 0.13 ships a `fetch` backend for this target, the socket is a small `web-sys` binding, and the loop's timers and channels come from `wasm-bindgen-futures` and `gloo` in place of tokio's. The loop is ported behind a socket and timer abstraction rather than rewritten, which is the next task. With Rust owning the transport, the JavaScript side holds the UI and a thin worker bridge, so **Effect is not adopted**; the decision reverses only if that port fails.
- **Encryption at rest** stays a VFS concern: `sqlite-wasm-rs` can build SQLite3MultipleCiphers or SQLCipher into the same module, which is the simplest way to keep the OPFS files unreadable without the per-origin WebCrypto key (architecture 11.4). To be chosen when the web device model lands.
