# Load test: the numbers of architecture section 17

Date: 2026-11-06. Code: `apps/instance`, `mix lumia.load` (`bench/`), and `mls_budget` in `apps/core/crates/lumia-core/src/mls/group.rs`. The first load test the architecture asked for in section 20: every row of section 17 the instance can measure, against the row's own workload where the laptop allows it, and the two intervals that were waiting on measurement.

## Setup

- Apple Silicon laptop (24 cores, 128 GB), one BEAM node, Postgres 18.4 local, Elixir 1.20.4 / OTP 29, Bandit, Phoenix 1.8. Clients are real WebSocket and HTTP/1.1 connections (`mint_web_socket`, `Mint`) in the same VM as the server, so they share its CPU.
- **Database of 10 million events**: 1,000 text channels in one server, 10,000 message events each, 1 KB bodies, inserted straight into `events`, `event_payloads` and `messages` in batches (120k events/s; 27 GB with indexes). The query shapes are the write path's; only the gateway is skipped.
- Dev compile with the code reloader left out (`LUMIA_CODE_RELOADER=false`): the reloader plug costs about 8 ms per HTTP request and sits on every upgrade too, which was most of the scrollback row before it was found. No TLS, no network RTT; the budgets' 20 ms RTT is additive and the TLS handshake lands on the connect row only.

Laptop numbers, clients sharing the server's CPU: shape and order of magnitude, not production capacity.

## Results

| Row (section 17) | Workload run | p50 | p99 | Budget |
|---|---|---|---|---|
| Send to delivered | 50 members on one channel, 1 KB bodies, 300 messages at 10/s, 10 background writes/s across the other 999 channels | 6.4 ms | 18.2 ms | 100 ms |
| Gateway connect, authenticate, resume 50 channels, presence | fresh session each time, cursors at every head, `PresenceUpdate` watching the server; from before the TCP connect to `SubscribeResult` | 65.7 ms | 77.7 ms | 500 ms |
| Scrollback of 50 messages | `GET /channels/{id}/messages?limit=50` at random channels and offsets over the 10M, keep-alive | 1.4 ms | 2.3 ms | 50 ms |
| Protobuf frame, plain message, less the body | `ServerFrame` with a `MessageCreated` event, ids, timestamps and `acl_version` set | 177 bytes | | was 64, now 200 |
| MLS encrypt / decrypt | 10-member group, 1 KB operation, release build (`mls_budget`) | 43 µs / 55 µs | 63 µs / 83 µs | 1 ms |
| Concurrent connections, delivery | 10,000 sessions in a VM of their own, 50 subscriptions each at the heads, a tenth in presence, 10 messages/s to random channels (about 500 subscribers each) | 12.8 ms | 28.0 ms | 100 ms |
| Concurrent connections, memory | the same, the server VM's RSS before and after, from the OS | 585 KB each | | 100k in 8 GB, so 80 KB each |

Send to ack tracks send to delivered within a millisecond, as in the gateway spike: the commit is the floor and the fan-out rides on it.

**The frame budget was wrong, not the frame.** An event frame carries the event envelope (event id, channel id, seq, command id, actor, timestamp, acl version) and inside it the message with its own ids and timestamp, 16-byte ids each costing 18 bytes on the wire. 177 bytes is what the protocol as specified costs; about 66 of them repeat the message's ids and timestamp in the envelope. The budget is now 200 bytes (a reply's `parent_id` adds 18). Collapsing the duplication would be a wire change on every client for a saving smaller than one TCP header, so it is noted, not done.

**The MLS ciphertext** for a 1,024-byte operation is 1,212 bytes, the E2EE overhead the table said it would budget once the framing was pinned: 188 bytes.

**The connections row misses, twice.** The delivery budget holds under 10,000 connections, but:

- **Memory: 585 KB of RSS per connection**, seven times the 80 KB the budget implies. Read from the server VM at 1,000 and 2,000 connections: a session process keeps 33 to 139 KB of heap (the subscriptions map and what the subscribe burst left before a collection) and its transport 35 to 45 KB; the PubSub registry holds about 175 bytes per subscription; and `:prometheus_metrics_dist`, the table where `TelemetryMetricsPrometheus.Core` keeps every distribution sample until the next scrape aggregates it, had 305,717 rows and 57 MB after 1,000 connections, one row per repo query (150 per subscribe) and per request, growing without bound on an instance nothing scrapes. That one is fixed: the instance aggregates its own metrics every 30 seconds. What remains unattributed is about 250 KB of refc binaries per connection that no process heap and no sampled ETS row references; the sockets' driver buffers are the first suspect, and the plan carries it.
- **The connect rate: about 100 sessions a second**, with a pool of 40 and 50 subscriptions each. A subscribe is three queries per channel today (the access, the head, the empty replay page), 150 per session, and a ramp past what the pool serves makes DBConnection drop queued queries after its 50 ms target, which crashes the session mid-subscribe and answers later upgrades with a 500 (seen at 200/s with a pool of 40, and at any rate with the dev pool of 10). At 100 a second, 100,000 clients reconnecting after a restart would take a quarter of an hour, and a storm faster than that takes the node down with them. The fix is the same one the connect row wants: resolve a subscribe per server, not per channel (one membership read, the channels and heads in one query, no page read when the cursor is at the head), and a connect backoff on the client with jitter, as the delivery spec's resume already describes. Both are noted in the plan as what the connections row needs before the budget can be claimed.

## The intervals of section 20

Measured on the same fixture:

| Cost | p50 | p99 |
|---|---|---|
| One reconciler tick with every one of the 1,053 channels having moved in the window (the query plus a node-local broadcast per head) | 2.3 ms | 2.5 ms |
| One re-resolution of a subscription (`Access.channel/2`: channel, membership, roles, overwrites) | 0.33 ms | 0.66 ms |

- **Reconciler tick stays at 5 seconds with the 1-second overlap.** The tick is proportional to the channels written in the window, not to subscriptions, and costs about 2 µs per active channel; an instance with 10,000 channels written every 6 seconds would spend 20 ms of one process per tick. The tick is the bound on commit-then-die delivery and on the member-level removal case (authorization section 5), so shortening it buys latency on a rare path at a linear cost, and lengthening it buys nothing the budget needs.
- **Bounded staleness stays at 10 minutes.** A re-resolution is under a millisecond and happens only before a delivery to a stale subscription, so its cost is bounded by the delivery rate, not by the subscription count: at most one extra query per subscription per 10 minutes, and only for subscriptions that receive something. At 100,000 connections with 50 subscriptions each all receiving a message within the window, that is 5 million re-resolutions per 10 minutes, 8,300/s at 0.3 ms each, about 2.5 cores: the ceiling for the whole node at the connection budget, paid only under that load. The bound's purpose is the partition case (a node rejoining marks every subscription stale, and each is re-resolved on its next delivery rather than all at once); 10 minutes keeps that trickle slow and the window in which a pre-partition view can serve a quiet channel small enough to state.

Both values are now recorded as measured in architecture section 7.4, delivery section 11 and authorization section 10.

## Reading

- **Every instance row but the connections row is under budget on the 10M database**, the send row by a wide margin, the connect row by seven times. The connect row is 50 subscriptions resolved one after another, three queries each (access, head, the empty replay page); batching the resolution per server would take most of it out, and is the first thing to do if the row ever moves.
- **Postgres autovacuum after the bulk load moved the send row.** The first run after seeding, with the autovacuum workers over the new partitions, gave 7 ms p50 and 54 ms p99 for the same workload (ack p99 55 ms: the commit, not the fan-out). The settled numbers in the table are from after it finished. A production instance does not bulk-load 10M rows, but a vacuum of a large partition is the kind of commit-latency event the p99 budget has to absorb, and it did, inside the 100 ms.
- **The dev reloader is a measurement hazard.** `Phoenix.CodeReloader` runs on every request and upgrade in dev whether or not anything changed, and `code_reloader` is compiled into the endpoint, so a runtime override does not remove it. `mix lumia.load` refuses to run with it in.
- **CI**: the instance workflow runs `mix lumia.load --ci` (a 100-channel, 100k-event fixture on a database of its own, every row but the connections, each p99 checked against its budget), and the core workflow runs `mls_budget` in release. The seeding takes a second; the whole step under a minute.

## Not measured here

TLS, a real network RTT, multi-node fan-out, the client rows (cold start, idle RSS, the Linux webview budget), and the 20 ms RTT and 10 msg/s TLS workload exactly as written. The connections row was measured at 10,000 on a laptop with the clients in a second VM, not at 100,000 on a 4 vCPU / 8 GB node; the per-connection memory and the connect rate are what extrapolate.
