This is the Lumia web UI (architecture section 13): SolidJS 1.9 with Vite, TanStack Solid Router, Solid Query and Solid Virtual, bun as package manager and script runner. It is the UI for the browser alone; the desktop apps are the native shell in `apps/desktop`. Read `../../docs/architecture.md` and `../../docs/plan.md` (step 6) before changing anything here.

## Layout

- `src/design/`: the design system. `components.tsx` is the port of the 36 components from the design artifact plus the ones added since (notice, request card, device list, empty state; the popover with the menu, the profile card, the small form and the choice that open in one; the quote, the reply bar, the note over the composer, the @ list, the emoji picker, "Quote reply" and a Mentions page's item) (same class names, markup and ARIA), `components.css` their stylesheet, `icons.ts` the 39 glyphs of `../../assets/icons`, `emoji.ts` the picker's emoji (`emojibase-data`'s list, loaded the first time a picker opens and slimmed by a plugin in `vite.config.ts`, written in the fully-qualified form every client reacts with) and this browser's most used, and `tokens.css` is GENERATED from `../../assets/design/tokens.json` by `scripts/tokens.ts` on every build; never edit it, edit the tokens. `tokens.css` carries the dark colours under `prefers-color-scheme` for a root with no `data-theme`, so the app follows the system as it changes unless Preferences holds Light or Dark, which is `data-theme` on the root (`client/preferences.ts`, the only thing in the app that sets it); the gallery sets it too, to show a board in either, and gives the page back to the preference when left. `AppShell` is a frame the size of the window (the page never scrolls; the sidebar's list, the message list, a page's body and the aside each scroll in themselves), with the aside (the member list, a conversation's details) shown and put away by the conversation header's toggle, remembered (`preferences.ts`, `asideHidden`), and below 1100 wide sliding over the conversation's end over a shade instead, the shade or Escape putting it away and, below 720, the frame folded as the iOS boards have it: the rail and the sidebar as one screen and what is being read as a panel over them with a back button.
- `src/routes/`: the route tree (code-based TanStack router). The root elects the owning tab; `/` reopens the saved instance and goes to `/app` or `/sign-in`; `/sign-in` (instance, trust card, password or a new account; with `?invite=` from an invite link, the account is created with the code or joins after signing in, and lands in the server), `/invite/$code` (the link an invite is, on the instance: the server and the instance's trust card before anything is sent, then join, sign in or create an account; `?instance=` names the instance when the UI is not served by one), `/link` (link this browser from a native device), `/app` (the Quiet Split: a server by `?server=`, or Home by `?place=home` with `view` and `dm`; in a server, the sidebar lists the channels the account is in and its server DMs, each section with a plus, and invitations above the channels, and a channel Browse lists can be read before joining with `JoinBar` where the composer would be (architecture 6.8); `channels.tsx` is Browse, "Your settings in" a server, a channel's members beside it (Add people, Remove, Leave channel) and the Default channels card; `server-settings.tsx` is a server's settings page (architecture 6.7: its picture, name, default channels and retention), shown in the server's main pane from the menu under its name to whoever may change them (`canManage`) until a channel is chosen; `home.tsx` holds the Home sidebar, conversation, requests, new message, add a server (create one, or join from a pasted link or code; the rail's "+" lands here too), profile, preferences (appearance and message density, each taking effect as it is chosen) and devices; `menus.tsx` holds what opens over the frame, one at a time: the menu under a server's name with its two popovers ("New channel", and "Invite people": a link with an expiry and a use limit to copy, one mailed to an address, and the server's invites with a revoke each), the account menu on the rail's self avatar (the status, View profile, Preferences, Devices, Sign out) and the Channels heading's plus (Create a channel, Browse channels), "Add people" and "Message someone" pickers, and the profile card a member's row or a message's author opens, which in a server offers a server DM and "Message privately"). A notice (`MessageSummary.notice`) is drawn as a `NoticeLine` and joins no block. A channel's and a conversation's messages are drawn by day and, within a day, in blocks (`byBlock` in `app.tsx`: one person's messages within five minutes of each other under one name; `density` on `MessageList` and `Message` draws them compact), and a server's channel says who is typing under the composer (`typingIn` in `state.ts`). `timeline.tsx` draws a conversation's messages for a server's channel, a server DM and a personal DM alike (architecture 6.6): each message with what it quotes (pressed, it jumps to the original, reading up to five more pages from the store, and flashes it), its mentions as pills (UTF-8 byte ranges), its reactions as chips, its own toolbar (the quick six, Add reaction with the picker, Reply), the row of one that names this account tinted, "Quote reply" beside text selected in one message, and the "New messages" line where the conversation's read position was when it opened; and the composer over it, with the reply bar, the @ list (a server's channel only) and the note a send leaves when someone mentioned is not in the channel (Add to the channel, Dismiss). A conversation is marked read (`createMarkRead`) while its newest message is on screen and the window has focus. Read state is the core's (`readStatesQuery` in `state.ts`, asked again after every event that can move it): unread rows in the strong ink with a count of mentions, a server's dot and count on the rail, Home's count, the Mentions row atop a server's sidebar and Home's (`mentions.tsx`, the page of `mentions`, paged as it scrolls, each item opening the channel at the message), and the badge, which is `setAppBadge` and the title's "(n) ", and which takes the shown notifications away at nothing unread (a push names no conversation, so they cannot be taken away one conversation at a time). `auth-page.tsx` is the page of the Sign in board, shared by sign-in, link, invite and the other-tab screen. `/design` is the gallery that rebuilds the design canvas's boards from the components with their sample data; it is how a change to the system is checked, in both themes.
- A build in `--mode instance` (`bun run build:instance`) is the one an instance serves: `SERVED_BY_INSTANCE` in `state.ts` makes the page's own origin the instance and hides the address field.
- `src/client/`: the bridge to the core. `worker.ts` runs `lumia-wasm`'s `Client` in a dedicated worker (OPFS sync access handles exist only there) and answers RPC calls; `bridge.ts` is its typed page side; `state.ts` holds the one bridge, the account snapshot and messages as Solid Query queries that the gateway's events invalidate, and presence by server from the gateway's diffs (`watchPresence` names the server on screen, re-sent on every welcome). `preferences.ts` is what the Preferences page holds, this browser's and not the account's: light, dark or as the system is, and comfortable or compact messages, kept in `localStorage` under `lumia:preferences` (anything not understood reads as the default), applied before the first render and followed from another tab. `autoscroll.ts` is autoscroll with the middle button held over any pane that scrolls, on every browser, by the desktop shell's numbers, with the browser's own (and Linux's middle-click paste) cancelled over a pane. `passkeys.ts` is the browser's own WebAuthn ceremony between the instance's options and its check (the Devices page makes passkeys, the sign-in page uses them). `pkg/` is GENERATED by `scripts/wasm.ts`.
- `e2e/run.ts`: the browser suite (Playwright, Chromium and WebKit, persistent contexts). It needs a dev instance on :4000 (`LUMIA_INSTANCE` names another) and the release CLI, which it uses as the other device (seeding, approving the link, asking for and answering a DM, minting the invite a fresh browser opens and creates an account from, mentioning the browser's account once it has gone away and while its Mentions page is open, trying a spent handoff token). The suite runs a push service of its own on :4919 for the Web Push step (Chromium only): a `pushManager` stand-in hands the app the suite's endpoint and keys, the app's own path registers the subscription, and the instance's push is decrypted here; the instance accepts that plain-http loopback endpoint only under `push_loopback_endpoints` (its dev and test configs).
- `../../assets` is the public root (`publicDir`): `/fonts`, `/brand`, `/icons`, `/design` resolve to the shared assets.
- Logic lives in the Rust core (`apps/core`, built to wasm and run in a worker); this app holds the UI and a thin bridge to that worker. Nothing here decides a protocol or storage question.

## Rules

- Solid, not React: props are read lazily (never destructured), `class` not `className`, `for` not `htmlFor`, `style` objects use CSS property names, lists are `<For>`, conditions `<Show>`.
- The screens mirror the desktop shell's (`apps/desktop/src/ui`) and the iOS app's: the same states, wording and error handling. A screen is checked against its board by looking at both, in light and dark, at the board's size.
- What the boards draw that the product has nothing behind (search, threads, saved, attachments, pins, calls, role tags, the composer's formatting, emoji and mention buttons) is not drawn in the app; a control that does nothing is worse than none. The gallery keeps drawing them, since it rebuilds the boards. Plan step 9 lists them.
- The design system's components are the vocabulary; a screen that needs a new element adds it to `components.tsx` with its CSS beside the others, named `lu-*`, and shows it in the gallery.
- Colours, spacing, radii, shadows and sizes come from tokens (`var(--…)`); no literal values in screen CSS.
- A field being typed in draws no focus ring (Ryan, 2026-11-13): its caret and border say it is focused. Buttons and links keep the ring for the keyboard.
- Sentence case everywhere, typographic punctuation, no emoji in chrome; the brand book in the design artifact and `assets/README.md` is the reference.
- `bun run check` (tokens, wasm, typecheck) and `bun run build` must pass; CI runs them. Run `bun run e2e` against a dev instance after a change to a screen or the bridge.
- Events from the worker are plain objects with camelCase fields (`rename_all_fields` on the Rust enum); the TypeScript `ClientEvent` in `bridge.ts` must match the Rust `ClientEvent` in `lumia-wasm/src/client.rs`.
