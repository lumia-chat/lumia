This is Lumia on Android (architecture section 13): `lumiakit`, the library the screens share, and `app`, the Compose layout for a phone. Read `../../docs/architecture.md` and `../../docs/plan.md` (step 7) before changing anything here.

## Layout

- `scripts/core.sh`: builds `lumia-ffi` as a shared library per ABI through `cargo-ndk` (arm64-v8a for devices, x86_64 for an Intel emulator; `--arm64` for devices only) into `lumiakit/src/main/jniLibs`, generates the Kotlin bindings with the workspace's `uniffi-bindgen` into `lumiakit/src/main/kotlin/uniffi` (what Kotlin needs named differently is `lumia-ffi`'s `uniffi.toml`: `BodyBlock.List` is `BodyBlock.ListBlock` here, a variant named `List` hiding Kotlin's own `List` from the variants' fields), and runs `scripts/tokens.py`, which writes `lumiakit/src/main/kotlin/chat/lumia/kit/Tokens.kt` from `../../assets/design/tokens.json`. Everything it produces is ignored by git; run it before any build, with `ANDROID_HOME` pointing at an SDK that has an NDK (`ANDROID_NDK_HOME` names one explicitly) and the Rust targets `aarch64-linux-android` and `x86_64-linux-android` installed.
- The core's TLS, `lumiakit`'s `Tls.kt`: the core's HTTPS (reqwest, and the link-card fetcher) verifies certificates with `rustls-platform-verifier`, which on Android asks the system's trust manager through a small Kotlin component of its own over JNI, so the phone's own trust store decides (and its revocation checks, where it has what they need). The verifier must be handed the application's `Context` once before the first request, or every HTTPS request fails ("Expect rustls-platform-verifier to be initialized"): `LumiaApp.onCreate` calls `Tls.initialize(this)` before any client is made (a push received with the app away starts the process through the application too). `Tls` loads `liblumia_ffi.so` with `System.loadLibrary` (UniFFI's JNA load does not make a native method findable) and its `external fun initialize` is `lumia-ffi`'s `Java_chat_lumia_kit_Tls_initialize` (`src/android.rs`, on the `jni` the verifier uses; a second call keeps the first's). The Kotlin component is the AAR `org.rustls:rustls-platform-verifier` from the Maven repository its makers keep on their GitHub repository's `maven-archive` branch (`settings.gradle.kts`, limited to the `org.rustls` group), at the version of `rustls-platform-verifier-android` in `../core/Cargo.lock`, which `lumiakit/build.gradle.kts` reads at configuration (the README's `ValueSource`) and names on the dependency itself, so a `cargo update` of the verifier moves the AAR with it and the two never differ. `app/proguard-rules.pro` keeps `org.rustls.platformverifier.**` for R8, which cannot see JNI's calls. The gateway's WebSocket is not this: `tokio-tungstenite` with webpki's roots (Mozilla's, built in), on every platform. The verifier's AAR also brings a network security configuration that refuses cleartext to all but the certificate authorities' revocation lists, and Android reads a configuration in place of the manifest's `usesCleartextTraffic`, so with it merged in the phone's own HTTP (`Pictures.kt`'s `HttpURLConnection`; the core's is not asked) was refused on an http instance, a development one at `10.0.2.2` or one hosted plainly on a home network: no person's or server's picture was drawn there, and `scripts/smoke.sh` stopped at the server's picture. The app's manifest therefore names its own (`res/xml/network_security.xml`, `tools:replace`), which permits cleartext as `usesCleartextTraffic` always said; found and fixed 2026-11-16, the smoke's picture steps seen passing after it. Checked on the emulator on 2026-11-16, debug and the R8 release build (signed with the debug key to install): the core's `instanceInfo` of `https://lumia-instance.fly.dev` and `resolveBlueskyHandle("bsky.app")` succeeded where before they failed with that message, and `https://expired.badssl.com` was refused.

- Push (architecture 15.5): `lumiakit`'s `Push.kt` is what every receiver shares: `PushRegistrar.received` opens a client of its own on the saved instance and calls the core's `notificationContent` (the same call the iOS extension makes, under the same writer lock, which is in-process on Android since the standard library's file lock is unsupported there and no second process exists), then posts the message as a notification whose tap carries the channel and kind; `subscribe` sends the endpoint or token to the instance once per value and instance, remembered as a mark by platform in the `push` shared preferences (`pushMark`), and sends nothing for a phone that is signed out or signing out; `left` is what leaving a session does about it: a sign-out asks the instance to drop each platform the phone remembers subscribing as (`pushUnsubscribe`), a session the instance ended cannot, and either way the marks are forgotten, so the next sign-in, as the same account or another, subscribes again, the phone's own registrations are given up (`PushRegistrar.unregister`, which the application sets to `PushSetup.unregister`, the libraries being the app's), and the notifications the phone is showing are cleared. A push that still reaches a signed-out phone (a subscription the instance could not be asked to drop) posts nothing, the generic notice neither: `received` asks the client it opens whether it is signed in. Every notification is tagged with its conversation's channel (the generic notice `lumia`) and numbered with the push's `badge`, which is what a launcher counts: Android has no badge an app sets. A read push (`kind=read`, a data message through the relay or UnifiedPush's notice) shows nothing: `readElsewhere` reads the counts again, through the session when the process has one and else a snapshot of a client of its own, and `settle` takes away the delivered notifications of conversations with nothing unread (all of them at a badge of 0) and numbers the rest with the badge; the session's `readsChanged` settles the same way whenever the counts change in the app, so a conversation read here takes its notifications with it. `app/.../push`: `LumiaPushService` (UnifiedPush: the distributor's endpoint and its Web Push keys as the `unified_push` subscription, under which the instance encrypts the notice; its messages as pushes), `LumiaFcmService` (FCM through the relay: the token as `fcm`, a data message naming the instance) and `PushSetup` (after sign-in, once per sign-in for the process however often the shell or the activity is made: the notification permission, a distributor when one is installed, FCM otherwise). A session left, signed out of or ended by the instance, gives the registration up (`PushSetup.unregister`): `UnifiedPush.unregister`, which tells the distributor and forgets the distributor chosen and the keys made for the endpoint, and FCM's `deleteToken`, each failing quietly; the next sign-in registers afresh and is handed an endpoint and keys of its own (with ntfy on the emulator: `UNREGISTER received`, the subscription removed, and another `https://ntfy.sh/up…` after signing in again). In a debug build `PushSetup.standIn`, the launch's `LUMIA_DEV_PUSH`, is an endpoint registering hands over in a distributor's place, with nothing asked of the person or of a distributor. It turns the phone on a screen reached by taps (the same process and screen, one gateway connection, the instance's sessions unchanged); stalls the relay, taps Sign out and turns the phone while that waits (the sign-in screen within 30 seconds, 16 with a subscription to take back, nothing said of a session ended, and within five seconds of it no gateway connection left open); turns the sign-in screen and leaves it for the launcher and comes back (still running, still the form). `scripts/smoke-unifiedpush.sh` sends a real push through an installed ntfy and ntfy.sh (needs the internet and an instance started with `LUMIA_HOST=10.0.2.2`, so by hand, not CI); a dev launch with `LUMIA_DEV_*` extras keeps a session already saved for that instance rather than signing the named handle in, which is why both smokes reinstall the app first.

## Rules

- Logic lives in the Rust core; `lumiakit` holds state and presentation, `app` holds layouts. A method a screen needs goes on `lumia_client::app::App` first, then through `lumia-ffi`.
- Colours, spacing, radii and type come from `LumiaTokens`; no literal values in composables. Sentence case, typographic punctuation, no emoji in chrome.
- The screens mirror the iOS app's and the web's: the same states, wording and error handling, so a change to one is a change to all.
- Build and test: `scripts/core.sh`, then `./gradlew :lumiakit:testDebugUnitTest assembleDebug` (the unit tests are the rules in `Timeline.kt`, `Preferences.kt`, `Leaving.kt`, `ServerSettings.kt`, `Membership.kt`, `Replies.kt`, `Body.kt`, `Emoji.kt`, `Rail.kt`, `Identity.kt`, `Media.kt`, `Embeds.kt` and `Pictures.kt`'s `avatarPathOf`; a rule that can be a plain value goes in one of them with a test). Run `scripts/smoke.sh` against a dev instance after a change to a screen or the session, and `scripts/smoke-signout.sh` after one to signing out, the store or what the activity keeps.
