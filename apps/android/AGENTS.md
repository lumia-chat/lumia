This is Lumia on Android (architecture section 13): `lumiakit`, the library the screens share, and `app`, the Compose layout for a phone. Read `../../docs/architecture.md` and `../../docs/plan.md` (step 7) before changing anything here.

## Layout

- `scripts/core.sh`: builds `lumia-ffi` as a shared library per ABI through `cargo-ndk` (arm64-v8a for devices, x86_64 for an Intel emulator; `--arm64` for devices only) into `lumiakit/src/main/jniLibs`, generates the Kotlin bindings with the workspace's `uniffi-bindgen` into `lumiakit/src/main/kotlin/uniffi`, and runs `scripts/tokens.py`, which writes `lumiakit/src/main/kotlin/chat/lumia/kit/Tokens.kt` from `../../assets/design/tokens.json`. Everything it produces is ignored by git; run it before any build, with `ANDROID_HOME` pointing at an SDK that has an NDK (`ANDROID_NDK_HOME` names one explicitly) and the Rust targets `aarch64-linux-android` and `x86_64-linux-android` installed.
- `lumiakit/src/main/kotlin/chat/lumia/kit`: `LumiaClient` (the UniFFI `Client` behind suspend calls on the IO dispatcher, the listener as a `Flow`), `LumiaSession` (Compose state: the snapshot, messages, DM channels and logs, the roster, the people, the connection state, presence by server from the gateway's diffs with `watchPresence` naming the servers on screen, and who is typing in the servers' channels, kept fresh by the gateway's events the way the web's queries are; `typed` says this person is typing, `typingIn` names who else is, and each is dropped when a message of theirs arrives or their time runs out, by one job that sleeps until then; a snapshot the instance refuses because the session is over, by `sessionOver`'s four codes, ends it on the phone as signing out does, and the sign-in screen says so once; a gateway loop that has ended asks for the snapshot, which says that or starts the loop again), `Timeline.kt` (the rules a conversation draws by, as plain values with no Compose in them: `joins` and `blockPlaces` for which messages are one block, `Typing` and `typingWords` for who is typing and how that reads; the desktop shell's rules, tested in `lumiakit/src/test`), `AppStore` (the one session and the route; reopens the saved instance, signs in from the launch intent's `LUMIA_DEV_*` extras in a debug build), `Design.kt` and the generated `Tokens.kt` (colours per theme, spacing, radii, type styles), `Presentation.kt` (initials, the nine avatar tones, times) and `Components.kt` (avatar, notice, empty state, message row, request card, device row, composer and the typing line under it, card, field, buttons).
- A conversation's messages, in a channel and a personal conversation alike: what one person sends close together (the same day, within five minutes of the message before) is one block, the avatar, the name and the time over the first and the rest under it a paragraph's distance apart, blocks 8 apart. A row under a block's first shows no time, there being no pointer to show it under; it says whose it is and when to TalkBack before its text, and every row is one stop for it. No send is drawn before the store holds it, so there is no pending row to place. Under the composer is the line that says who is typing (protocol 6.7), in a server's channel only: three dots and "Grace Hopper is typing…", two by name, "Several people" beyond; the dots are still when the system's animations are off. The line keeps its height when nobody is typing, in a personal conversation too, where it is always empty: the composer does not move as people start and stop, and sits where the boards draw it. Its room underneath (20) is not added to the navigation bar's but takes it in, the boards ending the line at the panel's foot where the bar lies.
- `app/src/main/kotlin/chat/lumia`: the phone layout, the Quiet Split folded as the design canvas's phone boards draw it and the iOS app lays it out: `Chrome.kt` (the rail, the sidebar header and tiles, `PanelScreen`: the floating panel a pushed screen draws itself in), `Shell.kt` (the rail beside Home's conversations or a server's channels as the root, a stack of screens the back button pops; opens the conversation a tapped notification names), `Screens.kt` (conversation, channel, requests, new message, add a server: create one or join from an invite link or code with its preview first, new channel, invite people: a link with an expiry and a use limit to copy or share, over the server's invites with a revoke each, devices with the revoke sheet), `SignInScreen.kt`, `LinkScreen.kt` and `MainActivity.kt` (one task; a notification's intent becomes the push target).
- Push (architecture 15.5): `lumiakit`'s `Push.kt` is what every receiver shares: `PushRegistrar.received` opens a client of its own on the saved instance and calls the core's `notificationContent` (the same call the iOS extension makes, under the same writer lock, which is in-process on Android since the standard library's file lock is unsupported there and no second process exists), then posts the message as a notification whose tap carries the channel and kind; `subscribe` sends the endpoint or token to the instance once per value. `app/.../push`: `LumiaPushService` (UnifiedPush: the distributor's endpoint and its Web Push keys as the `unified_push` subscription, under which the instance encrypts the notice; its messages as pushes), `LumiaFcmService` (FCM through the relay: the token as `fcm`, a data message naming the instance) and `PushSetup` (after sign-in: the notification permission, a distributor when one is installed, FCM otherwise). FCM is live only in a build with the Firebase project's `google-services.json` beside `app/build.gradle.kts`, which is not in the repo; without it the plugin is off and the token call fails quietly.
- Gradle: the wrapper (`./gradlew`), AGP and Kotlin from `gradle/libs.versions.toml`, `minSdk` 28 (Android 9), `compileSdk` 35; `JAVA_HOME` a JDK 17 or newer (Homebrew's `openjdk@21` here). The bindings need JNA, which the library declares.
- `scripts/release.sh [version]` builds the release (architecture section 13, "Distribution"): the core optimized and stripped for arm64 only, the APK signed with the release key named by `ANDROID_KEYSTORE_PATH`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS` and `ANDROID_KEY_PASSWORD` (unsigned without one, and named so), the version code the commit count, into `.build/dist/Lumia-<version>.apk`; `release.yml` runs it on a tag and attaches the APK to the GitHub Release. The keystore is the app's for life: Android installs an update only over the same key. `app/build.gradle.kts` takes the version and code as `-PlumiaVersion` and `-PlumiaBuild`; its own values are the development placeholders.
- `scripts/emulator.sh` creates and boots the headless emulator the smoke uses (an API 35 image for this machine's architecture); `scripts/smoke.sh` seeds a dev instance with the release CLI (the phone's account, and a second one joined through an invite the first mints, each with messages in the channel), installs the debug build, launches it once per screen with the `LUMIA_DEV_SCREEN` extra (home, server, channel, requests, devices, profile, new, add, newchannel, invite, signin, link) and screenshots each into `.build/smoke/`, which is how a change to a screen is checked. Then the channel as `uiautomator` reads it: each account's messages in a row must be one block (named once, the rest described for a screen reader), and the second account, typing through `lumia-cli typing`, must be named under the composer and gone after nine seconds of silence (`typing.png`, and `typing-dark.png` in the dark theme). Then push: the second account mentions the phone's account while the app is away, a launch with `LUMIA_DEV_SCREEN=notify` stands in for a push (the receivers' call, the notification posted, its content in `notification.txt`), and the notification's intent, as a tap sends it, must open the channel. Last, the script revokes the phone's session over HTTP, as signing out everywhere does, and the app must go back to the sign-in screen and say so (`revoked.png`), with the launch after that the sign-in screen and no line. The emulator reaches the host's instance at `10.0.2.2`. `scripts/smoke-unifiedpush.sh` sends a real push through an installed ntfy and ntfy.sh (needs the internet and an instance started with `LUMIA_HOST=10.0.2.2`, so by hand, not CI); a dev launch with `LUMIA_DEV_*` extras keeps a session already saved for that instance rather than signing the named handle in, which is why both smokes reinstall the app first.

## Rules

- Logic lives in the Rust core; `lumiakit` holds state and presentation, `app` holds layouts. A method a screen needs goes on `lumia_client::app::App` first, then through `lumia-ffi`.
- Colours, spacing, radii and type come from `LumiaTokens`; no literal values in composables. Sentence case, typographic punctuation, no emoji in chrome.
- The screens mirror the iOS app's and the web's: the same states, wording and error handling, so a change to one is a change to all.
- Build and test: `scripts/core.sh`, then `./gradlew :lumiakit:testDebugUnitTest assembleDebug` (the unit tests are the rules in `Timeline.kt`; a rule that can be a plain value goes there with a test). Run `scripts/smoke.sh` against a dev instance after a change to a screen or the session.
