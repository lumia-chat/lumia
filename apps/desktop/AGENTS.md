This is Lumia's desktop shell for macOS, Windows and Linux (architecture section 13): one Rust program on [Rune](https://github.com/anomalyco/rune) with the client core linked in. Read `../../docs/architecture.md` and `../../docs/plan.md` (step 9) before changing anything here. It has every screen the SwiftUI macOS app had and bundles as a Mac app; nobody has used it by hand yet, and there is no Windows or Linux package. Plan step 9 says what is open.

## Layout

- `Cargo.toml`: its own workspace on Rust 1.99.1 and edition 2024, Rune's pins. Rune and `rune-kit` are git dependencies at one pinned rev, and the manifest repeats Rune's four `[patch.crates-io]` entries (its patched `wgpu-hal`, `winit`, `parley_engine` and `accesskit_windows`), which a dependency cannot apply for the workspace that uses it. Bump every rev together, and compare the manifest's patches with Rune's own `[patch.crates-io]` at the new rev. The core is a path dependency on `../core/crates/lumia-client`, with `lumia-core` beside it for the core's media processing, which the scenes and tests make their sample attachments with as a send makes them; there is no binding layer. The workspace has two more members, `crates/sparkle` and `crates/appcast`, and all three are default members, so `cargo fmt`, `cargo clippy` and `cargo test` here cover them; `default-run` keeps `cargo run` the app.
- `crates/sparkle` (`lumia-sparkle`): the bridge to Sparkle, the macOS app's updater, and **the one place in this workspace where `unsafe` is allowed**. It loads `Sparkle.framework` from the bundle at run time instead of linking it and sends it Objective-C messages; its surface is five safe functions (start, check, can check, automatic read and set) on a type that cannot leave the main thread. Because it is where `unsafe` lives, it also carries what macOS only takes through AppKit (`src/system.rs`: the app's light or dark appearance and when its scroll bars show, from Preferences, the Dock icon's badge, and whether the system's clock is 24 hours, which the timeline's times follow). Its lints refuse an `unsafe` block without a comment saying why it is sound, or with more than one operation in it. Off macOS it is the same surface with nothing behind it and no dependencies.
- `crates/appcast` (`lumia-appcast`): the update feed off macOS, a Sparkle appcast signed as Sparkle's `sign_update` signs one (the feed's own signature in a comment after the document, over the bytes before it; each download's in its enclosure), with the same Ed25519 key. The library reads a feed, checks both signatures and compares versions for the Linux updater; the binary writes and checks the release's signed feed (`write`, `verify`, `public`). `tests/feed.rs` holds a feed Sparkle's own tool signed with a throwaway key and shows the two agree byte for byte, and the refusals: another key, no signature, a relabelled feed, a moved signature, a wrong download, an old feed.
- `.cargo/config.toml`: the macOS deployment target, 14.0, the same as `LSMinimumSystemVersion` in `packaging/macos/Info.plist`; change the two together. Left to rustc's default the Intel build targets 10.12 and links a Swift library by a run path the binary does not have, so that half of a universal app stops at launch.
- `build.rs`: turns the shared design assets into what the shell compiles in, as `apps/apple/scripts/tokens.py` does for Swift. `assets/design/tokens.json` becomes `tokens.rs` in `OUT_DIR` (every colour for light and dark as linear `Color`s, the shadows as `Shadow` layers, spacing, radii and sizes as points, the type styles), the WOFF2 fonts the tokens list become TrueType (Rune reads no WOFF2), on Linux with `fonts/NotoColorEmoji.woff2` beside them (Google's COLRv1 Noto Color Emoji, OFL, from googlefonts/noto-emoji at `99701e07`: Rune takes Linux's emoji from that family alone, by name, so a system with another emoji font or none drew boxes, #16), and `assets/icons`, the brand symbol and the stacked logo (through the sign-in boards' window on it) become Rune `Icon`s. Nothing generated is committed.
- `src/session/`: the client and the state the screens read, the counterpart of LumiaKit's `Session.swift`. It owns a tokio runtime; calls that reach the network run there and come back as `Update`s in a queue the window drains on its own thread (`Session::poll`), woken through a callback. Reads of the local store are synchronous. `mod.rs` is the account, its servers and the conversation on screen (a server's channel or a personal conversation, both read as `Entry`s); `dms.rs`, `servers.rs`, `channels.rs`, `identity.rs`, `avatars.rs`, `browser.rs`, `notices.rs`, `reads.rs` and `rail.rs` each hold one part of the product and report through their own update type (`Update::Dm`, `Update::Server`, `Update::Channel`, and so on). `channels.rs` is being in channels and server DMs (architecture 6.8 and 6.4): Browse's list, a channel read before joining (`Session::previewing`), each channel's members, joining, leaving, adding, invitations, this account's switches in a server and its default channels. `reads.rs` is architecture 6.6's read state (the core's counts, read again after each snapshot and applied event; `mark_read`), reactions, the Mentions lists and finding a message for a jump (`reveal`, reading further back up to five pages). `avatars.rs` is people's pictures as bytes: fetched once each, a few at a time, kept under `<host>/avatars/` for the next launch, and never asked of another host. People are held by account id (`Session::people`, from every server's member list in `Session::members`, and `Session::profiles` for those looked up), and every view names them through `name_of`, `person` and `avatar_url_of`, never from a copy. A changed name or picture arrives as the core's `AppEvent::ProfileUpdated` (#15): `Session::profile_updated` writes the account-level fields (handle, display name, picture, pronouns, bio) into every list that holds the person, each server's nickname and switches staying, holds someone held nowhere as a looked-up profile, takes this account's own into the snapshot (and reads the signed profile again), asks for the new picture and bumps `revision`; no member list is read again for it (`tests/profiles.rs`, `tests/live_profiles.rs`). A core call whose future is not `Send` (the identity and personal-conversation calls hold a store connection across their awaits) is run with `Session::task_local`. `identity.rs` also sets up private messages (#20, architecture 5.4): after every sign-in and at a launch that resumes a session, `Session::check_setup` runs the core's `identity_setup` silently, and what it comes to is `identity::Setup` (`Ready`, `Elsewhere` for an account whose identity is on another device, `NeedsReauth` when binding needs the password, `Failed`), with `phrase_kept` while the core keeps an unconfirmed phrase; personal conversations follow `Session::private_ready`, not `has_identity` alone. At launch the session starts from what the core kept of the account (`App::kept_snapshot`), and the open channel reads a page at a time, further back as the reader scrolls (`load_older`). **No toolkit type appears in this directory**: architecture 13 names GPUI as the fallback, and this is the part a move would keep.
- `src/app/`: the window's state over the session and its reactions to what the session reports. `mod.rs` is the frame: the route, the place (Home with a `HomeView`, or a server), the open popover, the draft, and `init`, `setup` and `poll` for Rune's `AppSpec`. `sign_in.rs`, `home.rs`, `server.rs` and `account.rs` hold each part's forms and its `react_*`. `setup.rs` is the forms of setting up private messages: the phrase (`Route::Phrase`: the words, then the three-word check; saved to a file only through the warning and then the save dialog, written readable by its owner alone), restoring (`Route::Restore`: first whether a device is still at hand, whose "Yes" is linking, then the words, then which of the devices restoring would stop to keep, `RestoreStep`), starting over (`Route::StartOver`), the password a setup that needs reauth takes, and Home's reminder with "In a week" (`settings.phrase_reminder_until`). Not built there: Print (Rune has no print dialog) and showing the phrase only after the computer's own unlock (no way to ask for one). Linking by a prompt (identity spec 4.2.1) is in two places: this computer as the new device is `account.rs`'s `Link` and `Prompted` (signed in, "Link from a device you use" opens a session at once and follows it to `linked`, which goes on as a claimed code; "Link another way" and sign-in's link are the copied request and typed code), and this computer holding the identity is `prompts.rs` (which prompt is on screen, its words, its calls, and when the sessions are asked about: once set up, the window coming in front, every `AccountApplied`, and every two seconds while one is open, from `State::tick`). "They match" approves with no unlock of the computer's own first, as Approve a device does. `State::receive` applies an update as if the instance had sent it, which is how tests stand in for one. A call whose answer belongs to a form and not to the session (an invite's preview, say) still travels as an `Update`: the session applies nothing and the form's `react_*` takes it. A computer another device removed (the core's `Closed` with `removed`, identity spec 4.4) goes to sign-in with `sign_in::REMOVED` over the card, the session and `settings.json` forgetting what they held of the account and the pictures kept under `<host>/avatars/` erased (`State::device_removed`, `Session::device_removed`). `pictures.rs` is the avatars and server pictures decoded for drawing (Rune's image cache, which is why it is here and not in the session); `ui::components::avatar_of` and `server_picture` draw one, with the initials under it only until it has decoded (a picture with transparency would show them through). `media.rs` is attachments and link cards in the window (specs/media.md 5 and 6) over `session/media.rs` (what waits in the composer's strip, the cards previewed, the pictures of the messages on screen as bytes, fetched a few at a time and checked with `App::attachment_drawable`, the core's cache under `<host>/media/`): the pictures and placeholders decoded, the attach button's file dialog, a paste (files, or a picture with no words) and a drop onto the conversation, the alt text of a waiting picture, the links previewed 500 ms after the words rest, the viewer (zoomed by the core's rules, `lumia_core::viewer` and specs/media.md 5, to four times a picture's own size: the wheel and a trackpad's pinch about the pointer, a press on the picture to its own size and back, the bar's −, Fit, 1:1 and + and the keys + − 0 1, a drag while zoomed, Escape), Save through the save dialog, a video or a recording written under the temporary directory by its media type's extension and opened by the platform on Linux (`media.to_open`), a GIF played by a press under Reduce Motion, and what an edit's × takes out (`edit_removed`, `edit_dropped`, sent by `Session::edit`). A send carries the uploaded files and the kept links and waits while one uploads (`State::can_send`). `playback.rs` is an attached video or recording played in the conversation on macOS and Windows with Rune's own `Player` (#21): nothing before a press, the file written by the session (`Session::write_for_inline`, `MediaUpdate::Written`) and played unless another was pressed since or its row left the view meanwhile (one write for a clip at a time; one whose file could not be fetched keeps a Play that asks again), what starting one stops and what stops off screen taken from the core's rules (`lumia_core::playback`: one clip playing at a time, a video paused when its row leaves the list's view, `State::rows_visible`, from the list's `on_visible_rows`, while a recording plays on), every clip and its file gone when its conversation leaves the screen (another opens, or a page takes its place: `State::conversation_shown`, which marking the conversation read asks too), full screen as the video over the window with the window taken full screen unless it already was (`Playback::settle_window`, carried out in `platform::settle` from what the window says of itself), never one the server let go; `Playback::inline` is `INLINE` (false on Linux, where Play opens the system's player) and a test may set it. `drafts.rs` is what is typed in a conversation's composer and not sent (#23, architecture 13): each conversation keeps its words and the reply they answer in the core's store (`Session::draft`, `Session::keep_draft` over `App::draft` and `App::set_draft`), read into the composer when the conversation comes under it (`State::tick`, at a launch too) and kept once the composer has rested 400 ms (`draft_wake` wakes the window for that), when the conversation leaves (`leave_draft`, which every place that changes the conversation calls before it forgets the reply), when the window goes behind another or closes and when the app quits (`platform`'s `on_close` and `on_quit`); a send and an emptied field keep nothing, the files waiting over the composer are not kept, and signing out empties the field without keeping it, the core forgetting the rest. `rail.rs` is the rail as the account arranges it (architecture 6.9): which folders are open on this computer (`settings.open_folders`), a tile's drag (what it is over, from where each tile was last laid out: a tile's top or bottom quarter is between, its middle half onto; Escape puts it back), the menus' moves and Folder settings, each an edit from `lumia_client::rail` sent whole by `Session::arrange_rail` (`session/rail.rs`, which shows the edit until the instance answers and goes back if it refuses), and what a screen reader is told of each move. `aside.rs` is where the aside (a server's member list, a conversation's details) goes: in the row in a window 1100 points or wider, put away and brought back by the header's toggle and remembered (`settings.aside_hidden`), and in a narrower one slid over the conversation's end by the same toggle, a press outside or Escape putting it away; the shell's layout reports the window's width. `channels.rs` is what the window holds of being in channels: the pages a server's main pane shows in place of a channel (Browse, "Your settings in" the server), the "Add people" and "Message someone" pickers, the default channels chosen in the server's settings, and the profile card's way to a server DM. `replies.rs` is architecture 6.6 in the window: the quote over the composer, the selection a "Quote reply" would quote, the row under the pointer, the emoji picker's message and "Frequently used" (`settings.recent_emoji`), the composer's @ list (what `@word` the caret is in, its rows, Up, Down, Return, Tab, Escape), the bar after a send naming those mentioned who are not in the channel, the message a jump flashed, and marking the open conversation read while its newest message is on screen in front of the person. `context.rs` is the menus a right-click opens (#25), where the pointer is, and the Menu key and Shift+F10 under the control the keyboard is on (Rune sends both to an element's `on_secondary_press`, the nearest one up from the pointer or the focus): a message's (`open_message_context`: by the toolbar's rules, so none on a notice, a deleted message or while one is being edited; what the press was on first, "Copy selection" when the message is in the timeline's selection, `replies.selected`, with "Quote reply" when the selection is inside it alone, and "Open link" and "Copy link" on a link, since a row with a menu takes the place of Rune's own Copy for its text; then Reply and Add reaction as the toolbar's, then what More actions holds) and a person's (`open_person_menu`, on a member's row, a message's avatar and name, and a conversation's row when it is with one other person: "View profile", which opens their card beside that control, and the ways to a conversation their card would offer there, `State::ways_to`, which the card asks too; a server DM the menu asked for and the instance refused opens the card to say why). `server_settings.rs` is a server's settings page (architecture 6.7): its name, picture, default channels and retention, and its Files card (what the files take, how long attachments are kept, what a full server does; specs/media.md 4.5), each card saved on its own, and "Show deleted messages" at the end of the Message history card, saved as it is turned (the core leaves deleted messages out of its reads where it is off, so the timeline re-reads the open conversation on every snapshot), offered in the menu under the server's name when `ServerSummary::can_manage`, and drawn in the server's main pane until a channel is chosen. `State::tick` is what the passing of time does, called from `poll` before every frame: it says this person is typing when the draft has changed (the composer has no hook for an edit) and stops showing those whose typing has run out, which nothing arrives to say.
- `src/ui/`: the views. `components.rs` is the design system's pieces (avatar, card, field, buttons, segmented choices full width or as wide as their words, a switch, a choice drawn as a picture, notice, panel, popover, menu). `shell.rs` is the Quiet Split's frame and the rail, `rail.rs` the rail's servers and folders (rounded squares, a closed folder's four small servers, an open one's tinted column, the line and the tile a drag shows, drawn at the root, and the menus and Folder settings), and `shell.rs` says where the window's traffic lights go (`TRAFFIC_LIGHTS`, the board's spot); `server.rs` fills it in a server (the public channels this account is in, its private ones under Private when there are any, and its server DMs, the sections 12 apart as the boards have them, Channels and Direct messages each with its plus; the open channel's members beside it, or the server's on a page), `channels.rs` draws Browse, Your settings, the bar with "Join" where a channel read before joining has its composer, and a channel's members with "Add people", "Remove" and "Leave channel", and `home/` at Home (one module per `HomeView`). `server_settings.rs` is that settings page. `link.rs` is the link screen (the prompt's waiting, digits and ends, or the copied request), and `prompt.rs` the card over the window when another device asks to be linked. `setup.rs` draws setting up private messages: the phrase, its check, restore and start over as cards like linking's, what Home's panes and Devices show while this computer is not set up (`needs_setup`), Home's reminder under the sidebar's tiles and Devices' "Recovery phrase not saved" card; the caution's amber is `tokens::caution`, which the design system does not name yet, and `tokens::secure` the same in green; `components::toned_notice` draws a conversation's notice in either (a personal conversation's in green, a server DM's in amber, architecture 6.4). `menus.rs` is the menu under a server's name (with "Server settings" for whoever may change them), the account menu on the rail's self avatar, the profile card a member's row or a message's avatar opens, and the menu a right-click on a person opens (`person_menu`; `with_person_menu` gives a control it). `conversation.rs` is the panel a channel and a personal conversation share (header, timeline, composer with who is typing under it) and `timeline.rs` its messages (and, through the same rows, Preferences' preview of sample messages, `timeline::samples`, which nothing in presses), drawn as Preferences' message settings say: grouped (one person's quick ones as a block) or one line (`12:04  Priya  words`, each message), with a reply's reference line, mention pills, reactions (unless hidden) and tint, a message being edited in place, and the "New" line; the list is marked `instant_changes` with no transition of its own, so a message, a conversation's messages and the list itself are there in the frame they arrive, with none of the growth stack's glide (#26). `replies.rs` draws those parts and the toolbar over the message under the pointer (with its More actions menu and the delete confirmation), the menu a right-click on a message opens (`message_context`, hung from a place with no size that `ui::view` draws where it was asked for, `context::AT`), the "Quote reply" button over a selection, the @ list, and the reply strip inside the composer and the bar under it; the toolbar, the button and the list are drawn at the root (`ui::view`), not in the rows, which the timeline bench says to keep (a listener per row for a selection or for the pointer leaving cost every frame of a fling a third more). `media.rs` draws attachments and cards under a message's words (pictures at their shape, at most 400 tall, several in a grid; the design system's file row with Play and Save; a video playing in its poster's place or under its row and a recording in its row, with the shell's controls, and the full-screen video at the root; cards by host, title and description, with a banner whole under them at the card's width and a squarer or small picture beside them, by the core's `CardSummary::picture_under`), the strip and the previews over the composer, the drop target and the viewer at the root; what has no board is said in its module comment. `emoji.rs` is the emoji picker (the `emojis` crate, up to Unicode 16, which the systems' fonts draw), `mentions.rs` the Mentions page of a server or of Home. `scroll.rs` is the scroll bar every pane that scrolls ends with (`.with_scroll_bar(key, look)`), and autoscroll with the middle button held (`app/autoscroll.rs`: the pane reports where it has scrolled, the bar's frame takes the middle button's drags, and the frame's poll moves the pane; a do-nothing hover handler on the pane keeps a primary press there, since Rune gives an element with a drag handler primary presses too and turns off selecting text in it). A popover, a menu or a card is returned from `ui::overlay` so it mounts at the root. Views read the state and call its methods; they never touch the runtime.
- `src/ui/body/`: a message's text, the shell's own renderer for the protocol's Markdown subset (protocol 14) over Rune's rich text. The core's parser (`lumia_client::body`, shared with the other clients) reads the source with `pulldown-cmark` and decides what is in the subset (what is not stays as typed; a link is one only to a web address); `mod.rs` draws the blocks as selectable texts and says what a copy of each takes. The timeline's list is the one selection group around them, which is why this is not the kit's `Markdown`: that is a group of its own and a drag stopped at the end of a message. A code block never wraps: it scrolls sideways inside itself (`scroll_x`; a trackpad or Shift with the wheel, no bar) and has a "Copy" in its corner while the pointer or the keyboard is in it (`State::copy_code`: the clipboard, "Copied" for 1.5 s, and the window's live region). A body taller than 14 lines at the width its row gives it is folded to 10 (`body::folded_lines`, `Fold`; the width comes from the list's laid-out width, `timeline::fold_of`, and the lines are measured with Rune's text measure only when the source could take that many), fading into the row's own fill, with "Show more"; which are open is `Session::unfolded`, forgotten when another conversation opens. A Mentions item's body has neither button, being pressed as a whole.
- `src/tokens.rs`: includes the generated tokens and adds what is derived from them: the avatar tone an id hashes to; `MessageType`, every type style of a message's row and of the composer scaled to the font size chosen in Preferences (the views take a row's type from it, never from the plain tokens); the metrics and type styles the design canvas's boards draw that `tokens.json` names only in a usage line or not at all (a primary button's 48 points, an avatar's initials), each as arithmetic on tokens with the board's number beside it; and the code style, strong weight and syntax colours of a message body, which the design system does not name yet. A value a board uses that the tokens cannot make is a gap to report, not a literal for a view.
- `tests/body.rs`: message bodies through a windowless runtime (each construct, what stays as typed, links, selection across messages and what it copies, in both layouts, a code block's sideways scroll and its Copy, a long message folded and opened, lines counted as wrapped). The composer's counter and its refusal over the limit on a message (`Session::room`, the core's `body::room`; the edit field has the same) are in `tests/shell.rs` and `tests/replies.rs`; the composer and the edit field grow to eight lines through `rune::auto_grow`, then scroll. `benches/timeline.rs`: frame CPU of the message list over 1,000 varied messages, `cargo bench --features profile --bench timeline`, and `-- --minimal` for the same in one line; run it before and after a change to a row (its `tick` workload is what a playing clip's quarter-second runs cost the list). The `bodies` scene draws every construct and a line per script with no instance (`--snap out.png --scene bodies --size 1180x2000`), `long-messages` long messages folded (one in a mention's wash) and opened, a code block wider than the conversation and a draft over the limit (`--size 1180x1900`), `media`, `media-links`, `media-viewer`, `media-viewer-zoomed`, `media-edit`, `media-playing` and `media-failed` attachments and cards in messages and the composer (`--size 1180x1500`), with Images and Embeds as links, the viewer, the viewer zoomed as far as it goes, a card's × while editing, a video and a recording playing in the conversation (Rune draws the video's frame headlessly; `src/scenes/clip.mp4` and `tone.m4a` are its samples, made with FFmpeg's test sources), and the two when their files could not be fetched; and `blocks` a channel where people send several messages close together, with an edited message, a join line and a message's reactions (`blocks-compact`, `blocks-minimal`, `blocks-avatars-hidden`, `blocks-reactions-hidden` and `blocks-font-20` the same with the Compact and Minimal presets, with avatars hidden, with reactions hidden and at the largest font size; `replies-minimal` the replies scene in one line, its reactions shown; `preferences` the Preferences page, and `preferences-custom` with settings no preset matches; `server-settings` a server's settings, with a picture on the rail; `pictures` Grace's picture in her server DM's row, the member list and her messages; `members-over` the member list over a narrow window, at `--size 900x700`; `channels`, `channels-menu`, `browse`, `channel-preview`, `server-dm`, `add-people`, `new-dm`, `your-settings` and `person-in-server` being in channels and server DMs; `rail-folders`, `rail-menu`, `folder-menu` and `folder-settings` the rail's folders, a server's and a folder's menus and Folder settings; `replies`, `message-toolbar`, `message-menu`, `edit-message`, `delete-message`, `mention-list`, `emoji-picker` and `mentions` quote replies, editing and deleting, reactions, mentions and read state; `message-context`, `message-context-selection` and `person-menu` the menus a right-click opens, a message's, one over a selection and a link, and a person's; `sign-up`, `home-reminder`, `devices-phrase`, `needs-setup`, `devices-elsewhere`, `needs-reauth`, `phrase`, `phrase-save`, `phrase-check`, `restore-ask`, `restore`, `restore-keep` and `start-over` setting up private messages, #20, and `removed` the sign-in card of a computer another device removed; `link-waiting`, `link-compare`, `link-declined`, `link-expired` and `link-another-way` this computer linking by a prompt, and `prompt-new`, `prompt-web`, `prompt-waiting`, `prompt-compare`, `prompt-refused` and `prompt-linked` the prompt over the window of a computer that holds the identity).
- `src/settings.rs`: the data directory (`LUMIA_DATA_DIR`, else `chat.lumia` under the platform's application-data directory) and `settings.json` (the instance to reopen, the channel last on screen, which a launch returns to, and what Preferences holds: appearance, the message settings and scroll bars, each read as its default alone when it is missing or not understood, so an older or newer file still reads). The message settings are `layout`, `spacing`, `avatars`, `font_size`, `images`, `embeds` and `reactions` (shown or hidden: hidden, the timeline draws no row of chips and leaves no room for one, and the toolbar's "Add reaction" stays); the presets (`Preset`: Comfortable, Compact, Minimal) are values that write them, never stored, and `Preset::matching` is the rule for which one the page shows. The stores under it follow `lumia-ffi`'s layout: `<host>/store.sqlite`, `<host>/keys.sqlite`, `identity/`.
- `tests/`: the screens through a windowless `rune::Runtime` with no instance, one file per part (`shell.rs`, `drafts.rs`, `context.rs`, `rail.rs`, `aside.rs`, `home.rs`, `servers.rs`, `channels.rs`, `replies.rs`, `server_settings.rs`, `account.rs`, `setup.rs`, `prompts.rs`, `profiles.rs`, `preferences.rs`, `media.rs`, `playback.rs`, `links.rs`, `notices.rs`, `menu.rs`, `instance.rs`); `common/` is what they share (a state, the gestures, a right-click among them, what an instance would report), and its `press` scrolls to its target first. `live*.rs` are the same shell against a real instance, with `lumia-cli` as the other people and devices: sending and a second launch from what was kept, history paged and scrolled back to a channel's first message, linking, personal conversations, the account screens, servers and invites, a server's settings and a changed name and picture reaching another member, who is typing between two shells, the browser handoff, a notification, and setting up private messages (`live_setup.rs`: a new account set up silently and its phrase checked, restored on a second computer, started over on a third, a CLI account with no identity set up at its next sign-in, and a second computer linked from Devices' Approve a device and by a prompt with matching digits). Each skips itself without `LUMIA_DEV_INSTANCE` (and `LUMIA_CLI`, and for `live.rs` an account in `LUMIA_DEV_HANDLE` and `LUMIA_DEV_PASSWORD`).
- `scripts/smoke.sh`: seeds a dev instance with the release CLI and checks the debug shell against it: signed in, snapshot loaded, gateway connected, messages and members in the tree, a message typed into the composer reaching the instance, and then every test with the live tests' environment (only `live_app.rs`, which launches a real bundle and so takes the `lumia:` scheme on the Mac, is left to skip itself). It draws `out/smoke/shell.png` and `shell-dark.png` headlessly through Rune's `--snap`, which needs no window and no screen-recording permission; a scene from `src/scenes.rs` drawn the same way is how a change to a screen is looked at. `scripts/startup.py` times a launch to its first frame over a signed-in data directory (`cargo build --profile perf` first).
- `src/platform/`: what makes the shell an app around the window, and the only place that meets the system. `mod.rs` is the hooks `main` gives Rune (`on_open_url`, `on_focus`, the poll that pays what the state owes: pages to open, notices to post, the frame for AppKit to remember, the menu's items); its module comment says what each platform gets today and needs. `updates.rs` holds the updater (`lumia-sparkle`) on the main thread and is what the menu's two update items do; only a real launch of a bundle that names a feed has one. `appimage.rs` is the Linux AppImage's own updater (Linux only): it has one when the AppImage runtime started this process from a file (`APPIMAGE`, with the executable inside `APPDIR`) and the build compiled in `LUMIA_UPDATE_FEED` and `LUMIA_UPDATE_KEY`; it pays what `app/updates.rs` owes (check, download and rename over the AppImage, restart), on threads of its own, and a restarted copy waits in `main` for the old one to exit before it claims the data directory. Its unit tests serve a feed and a download from a local socket and run on Linux only. `system.rs` carries Preferences out where the system has a say (macOS: the app's appearance, and when scroll bars show), only in a real window. `instance.rs` is one running copy per data directory: a lock on `instance.lock` held for the process's life, and on Unix a socket a later launch hands its `lumia:` links to.
- `src/app/links.rs`, `notices.rs`, `menu.rs` with `src/session/browser.rs` and `notices.rs`: sign-in through the system browser and the `lumia:` link it returns on (every sign-in the shell starts carries a `state` the link must bring back; read the module comment before loosening it), the web page opened as this account, which message is owed a notification and what its click opens, and the menu bar's own items: the Account menu, the application menu's "Preferences…" (Command-comma, once signed in), and its "Check for updates…" and "Check for updates automatically" while there is an updater.
- `src/app/updates.rs` with `tests/updates.rs`: the on-screen updater where the platform carries one (the AppImage): its phases, what the window owes the platform, the daily check (`settings.update_checks`, `last_update_check`), and Preferences' Updates card and the sidebar's foot that show it (the `updates` scene). Nothing is downloaded without the person's Update.
- `scripts/dist-linux.sh` and `scripts/dist-windows.sh` with `packaging/linux` and `packaging/windows`: the preview packages a release tag publishes for the other two desktops (an AppImage with its signed `appcast-linux-<arch>.xml`, a `.deb` and an `.rpm` carrying the package repository's source and key, and a tarball with `packaging/linux/README.txt`, which does not update; a zip of `Lumia.exe` cross-built with MinGW-w64). `scripts/linux-repo.sh` makes the signed apt and dnf repository from a release's packages, which `.github/workflows/packages.yml` deploys to GitHub Pages, called by the release or run by hand on `master` to change the page or the script between releases; `packaging/linux/lumia-archive-key.asc` is its public key and `repository.html` its page. Each script's head says what it checks and what it cannot; run them in a container before changing the release workflow's jobs.
- `scripts/bundle-macos.sh` with `packaging/macos/Info.plist`: makes `out/Lumia.app` (bundle identifier, version and build number, the `lumia:` scheme, the icon from the brand symbol, the update feed and its public key, `Sparkle.framework` from the release pinned at the script's head, a signature made inside out) and checks it. `scripts/dist-macos.sh VERSION` is the macOS release path: the disk image (`Lumia-<version>.dmg`, which a person downloads and an update installs from), signed, notarized and stapled when the Developer ID and the notary's credentials are in the environment, and the signed `appcast.xml`, with a delta from a previous release. Its signing and notarizing branch has not been run yet. `scripts/update-check.sh` proves the update end to end on this Mac under a scratch bundle identifier with throwaway keys: an installed build updating itself from a feed served locally, and the five releases it must refuse; run it after a change to the bridge, the bundle's update keys, the pin or either script. `tests/live_app.rs` launches a debug bundle for real (`LUMIA_DEV_APP`); `tests/live_browser.rs` and `tests/live_notice.rs` run the handoff and a personal message's notice against an instance with no window.

## Rules

- A link opened with the app, a later launch's arguments and a clicked notification's contents come from outside the app. They are parsed strictly and may only do what `State::open_url` and `State::open_notice` allow: complete a sign-in this app started, or show a conversation this account already has.
- A debug build's `LUMIA_DEV_BROWSER` and `LUMIA_DEV_TRACE` exist so a real launch can be checked with no hands on the window; a release build ignores them, as it ignores `LUMIA_DEV_INSTANCE`.

- Logic lives in the Rust core. A call a screen needs goes on `lumia_client::app::App` first; `session.rs` holds state and the views hold layout.
- Colours, distances, radii, shadows and type come from `tokens`; no literal values in views. Sentence case, typographic punctuation, no emoji in chrome.
- The screens mirror the web's (`apps/web/src/routes`) and the iOS app's (`apps/apple/Lumia-iOS`): the same states, wording and error handling.
- A screen is checked against its board by looking at both: draw the board (the design canvas's `.dc.html` in a browser at the board's size) and the shell (`--snap` at the same `--size`) and put the same region of each side by side. Reading the board's styles alone has passed over what a glance shows, such as a list anchored to the wrong end of its pane.
- Every interactive element has a role, a label, a focus ring and a key; a list is a `list` of `listitem`s. The accessibility tree is part of the screen (`--tree out.json` shows it).
- A message is text someone else wrote. Its links open only as `http` or `https`, and the shell fetches nothing a message names: no URL in a message is ever asked for. What the shell fetches that someone else chose is an avatar, only from the instance it is signed in to, whose bytes the instance encoded itself (`session/avatars.rs`), and a message's attachments and cards' pictures (specs/media.md), only through the core (`App::attachment_bytes`, checked against their hash; `App::card_image`, a path of this instance), each checked with `App::attachment_drawable` before it is decoded. A card's link is opened only as the message's words have it; a file is opened only through the save dialog, or a video or recording by Rune's player or the system's under an extension its media type gives, never the name its sender chose. A picture named on another host is not fetched, and the only page this computer reads is one the person typed a link to in a personal conversation's composer, which the core fetches by spec 6.3's rules to build its card (spec 6.5), never a link in a message received.
- No `unwrap` or `expect` outside tests, and no `unsafe` (manifest lints); `crates/sparkle` is the exception for `unsafe` and says so in its manifest. What needs `unsafe` goes there, behind a safe function, not into the shell.
- The Linux repository is trusted through `packaging/linux/lumia-archive-key.asc`, whose secret half is the release's `LINUX_REPO_KEY` and never in the repository. A package carries the key it was built with, so changing it means a release carrying both first (the head of `scripts/linux-repo.sh`).
- The update feed is trusted through one key: `SUPublicEDKey` in the bundle, whose private half is never in the repository. The feed and every download are signed with it (`SURequireSignedFeed`, which needs `SUVerifyUpdateBeforeExtraction`); neither is to be turned off. Do not run Sparkle's `generate_keys`, which writes to the login Keychain. Moving the Sparkle pin means changing the version and the SHA-256 together and running `scripts/update-check.sh`.
- `cargo fmt`, `cargo clippy --all-targets -- -D warnings` and `cargo test` must pass, and `scripts/smoke.sh` against a dev instance after a change to a screen or the session.
- What the shell does not do yet is listed in plan step 9. Say so in the screen's module comment when a flow is missing, and do not draw a control for it.
