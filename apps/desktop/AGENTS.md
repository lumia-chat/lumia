This is Lumia's desktop shell for macOS, Windows and Linux (architecture section 13): one Rust program on [Rune](https://github.com/anomalyco/rune) with the client core linked in. Read `../../docs/architecture.md` and `../../docs/plan.md` (step 9) before changing anything here. It has every screen the SwiftUI macOS app had and bundles as a Mac app; nobody has used it by hand yet, and there is no Windows or Linux package. Plan step 9 says what is open.

## Layout

- `Cargo.toml`: its own workspace on Rust 1.99.1 and edition 2024, Rune's pins. Rune and `rune-kit` are git dependencies at one pinned rev, and the manifest repeats Rune's four `[patch.crates-io]` entries (its patched `wgpu-hal`, `winit`, `parley_engine` and `accesskit_windows`), which a dependency cannot apply for the workspace that uses it. Bump every rev together, and compare the manifest's patches with Rune's own `[patch.crates-io]` at the new rev. The core is a path dependency on `../core/crates/lumia-client`; there is no binding layer. The workspace has one more member, `crates/sparkle`, and both are default members, so `cargo fmt`, `cargo clippy` and `cargo test` here cover it.
- `crates/sparkle` (`lumia-sparkle`): the bridge to Sparkle, the macOS app's updater, and **the one place in this workspace where `unsafe` is allowed**. It loads `Sparkle.framework` from the bundle at run time instead of linking it and sends it Objective-C messages; its surface is five safe functions (start, check, can check, automatic read and set) on a type that cannot leave the main thread. Because it is where `unsafe` lives, it also carries what macOS only takes through AppKit (`src/system.rs`: the app's light or dark appearance and when its scroll bars show, from Preferences, the Dock icon's badge, and whether the system's clock is 24 hours, which the timeline's times follow). Its lints refuse an `unsafe` block without a comment saying why it is sound, or with more than one operation in it. Off macOS it is the same surface with nothing behind it and no dependencies.
- `.cargo/config.toml`: the macOS deployment target, 14.0, the same as `LSMinimumSystemVersion` in `packaging/macos/Info.plist`; change the two together. Left to rustc's default the Intel build targets 10.12 and links a Swift library by a run path the binary does not have, so that half of a universal app stops at launch.
- `build.rs`: turns the shared design assets into what the shell compiles in, as `apps/apple/scripts/tokens.py` does for Swift. `assets/design/tokens.json` becomes `tokens.rs` in `OUT_DIR` (every colour for light and dark as linear `Color`s, the shadows as `Shadow` layers, spacing, radii and sizes as points, the type styles), the WOFF2 fonts the tokens list become TrueType (Rune reads no WOFF2), on Linux with `fonts/NotoColorEmoji.woff2` beside them (Google's COLRv1 Noto Color Emoji, OFL, from googlefonts/noto-emoji at `99701e07`: Rune takes Linux's emoji from that family alone, by name, so a system with another emoji font or none drew boxes, #16), and `assets/icons`, the brand symbol and the stacked logo (through the sign-in boards' window on it) become Rune `Icon`s. Nothing generated is committed.
- `src/session/`: the client and the state the screens read, the counterpart of LumiaKit's `Session.swift`. It owns a tokio runtime; calls that reach the network run there and come back as `Update`s in a queue the window drains on its own thread (`Session::poll`), woken through a callback. Reads of the local store are synchronous. `mod.rs` is the account, its servers and the conversation on screen (a server's channel or a personal conversation, both read as `Entry`s); `dms.rs`, `servers.rs`, `channels.rs`, `identity.rs`, `avatars.rs`, `browser.rs`, `notices.rs`, `reads.rs` and `rail.rs` each hold one part of the product and report through their own update type (`Update::Dm`, `Update::Server`, `Update::Channel`, and so on). `channels.rs` is being in channels and server DMs (architecture 6.8 and 6.4): Browse's list, a channel read before joining (`Session::previewing`), each channel's members, joining, leaving, adding, invitations, this account's switches in a server and its default channels. `reads.rs` is architecture 6.6's read state (the core's counts, read again after each snapshot and applied event; `mark_read`), reactions, the Mentions lists and finding a message for a jump (`reveal`, reading further back up to five pages). `avatars.rs` is people's pictures as bytes: fetched once each, a few at a time, kept under `<host>/avatars/` for the next launch, and never asked of another host. A core call whose future is not `Send` (the identity and personal-conversation calls hold a store connection across their awaits) is run with `Session::task_local`. At launch the session starts from what the core kept of the account (`App::kept_snapshot`), and the open channel reads a page at a time, further back as the reader scrolls (`load_older`). **No toolkit type appears in this directory**: architecture 13 names GPUI as the fallback, and this is the part a move would keep.
- `src/app/`: the window's state over the session and its reactions to what the session reports. `mod.rs` is the frame: the route, the place (Home with a `HomeView`, or a server), the open popover, the draft, and `init`, `setup` and `poll` for Rune's `AppSpec`. `sign_in.rs`, `home.rs`, `server.rs` and `account.rs` hold each part's forms and its `react_*`. `State::receive` applies an update as if the instance had sent it, which is how tests stand in for one. A call whose answer belongs to a form and not to the session (an invite's preview, say) still travels as an `Update`: the session applies nothing and the form's `react_*` takes it. `pictures.rs` is the avatars and server pictures decoded for drawing (Rune's image cache, which is why it is here and not in the session); `ui::components::avatar_of` and `server_picture` draw one, with the initials under it only until it has decoded (a picture with transparency would show them through). `rail.rs` is the rail as the account arranges it (architecture 6.9): which folders are open on this computer (`settings.open_folders`), a tile's drag (what it is over, from where each tile was last laid out: a tile's top or bottom quarter is between, its middle half onto; Escape puts it back), the menus' moves and Folder settings, each an edit from `lumia_client::rail` sent whole by `Session::arrange_rail` (`session/rail.rs`, which shows the edit until the instance answers and goes back if it refuses), and what a screen reader is told of each move. `aside.rs` is where the aside (a server's member list, a conversation's details) goes: in the row in a window 1100 points or wider, put away and brought back by the header's toggle and remembered (`settings.aside_hidden`), and in a narrower one slid over the conversation's end by the same toggle, a press outside or Escape putting it away; the shell's layout reports the window's width. `channels.rs` is what the window holds of being in channels: the pages a server's main pane shows in place of a channel (Browse, "Your settings in" the server), the "Add people" and "Message someone" pickers, the default channels chosen in the server's settings, and the profile card's way to a server DM. `replies.rs` is architecture 6.6 in the window: the quote over the composer, the selection a "Quote reply" would quote, the row under the pointer, the emoji picker's message and "Frequently used" (`settings.recent_emoji`), the composer's @ list (what `@word` the caret is in, its rows, Up, Down, Return, Tab, Escape), the bar after a send naming those mentioned who are not in the channel, the message a jump flashed, and marking the open conversation read while its newest message is on screen in front of the person. `server_settings.rs` is a server's settings page (architecture 6.7): its name, picture, default channels and retention, each card saved on its own, and "Show deleted messages" at the end of the Message history card, saved as it is turned (the core leaves deleted messages out of its reads where it is off, so the timeline re-reads the open conversation on every snapshot), offered in the menu under the server's name when `ServerSummary::can_manage`, and drawn in the server's main pane until a channel is chosen. `State::tick` is what the passing of time does, called from `poll` before every frame: it says this person is typing when the draft has changed (the composer has no hook for an edit) and stops showing those whose typing has run out, which nothing arrives to say.
- `src/ui/`: the views. `components.rs` is the design system's pieces (avatar, card, field, buttons, segmented choices, notice, panel, popover, menu). `shell.rs` is the Quiet Split's frame and the rail, `rail.rs` the rail's servers and folders (rounded squares, a closed folder's four small servers, an open one's tinted column, the line and the tile a drag shows, drawn at the root, and the menus and Folder settings), and `shell.rs` says where the window's traffic lights go (`TRAFFIC_LIGHTS`, the board's spot); `server.rs` fills it in a server (the public channels this account is in, its private ones under Private when there are any, and its server DMs, the sections 12 apart as the boards have them, Channels and Direct messages each with its plus; the open channel's members beside it, or the server's on a page), `channels.rs` draws Browse, Your settings, the bar with "Join" where a channel read before joining has its composer, and a channel's members with "Add people", "Remove" and "Leave channel", and `home/` at Home (one module per `HomeView`). `server_settings.rs` is that settings page. `menus.rs` is the menu under a server's name (with "Server settings" for whoever may change them), the account menu on the rail's self avatar and the profile card a member's row or a message's avatar opens. `conversation.rs` is the panel a channel and a personal conversation share (header, timeline, composer with who is typing under it) and `timeline.rs` its messages, drawn as Preferences' message settings say: grouped (one person's quick ones as a block) or one line (`12:04  Priya  words`, each message), with a reply's reference line, mention pills, reactions and tint, a message being edited in place, and the "New" line. `replies.rs` draws those parts and the toolbar over the message under the pointer (with its More actions menu and the delete confirmation), the "Quote reply" button over a selection, the @ list, and the reply strip inside the composer and the bar under it; the toolbar, the button and the list are drawn at the root (`ui::view`), not in the rows, which the timeline bench says to keep (a listener per row for a selection or for the pointer leaving cost every frame of a fling a third more). `emoji.rs` is the emoji picker (the `emojis` crate, up to Unicode 16, which the systems' fonts draw), `mentions.rs` the Mentions page of a server or of Home. `scroll.rs` is the scroll bar every pane that scrolls ends with (`.with_scroll_bar(key, look)`), and autoscroll with the middle button held (`app/autoscroll.rs`: the pane reports where it has scrolled, the bar's frame takes the middle button's drags, and the frame's poll moves the pane; a do-nothing hover handler on the pane keeps a primary press there, since Rune gives an element with a drag handler primary presses too and turns off selecting text in it). A popover, a menu or a card is returned from `ui::overlay` so it mounts at the root. Views read the state and call its methods; they never touch the runtime.
- `src/ui/body/`: a message's text, the shell's own renderer for the protocol's Markdown subset (protocol 14) over Rune's rich text. `parse.rs` reads the source with `pulldown-cmark` and decides what is in the subset (what is not stays as typed; a link is one only to a web address), with no toolkit type in it; `mod.rs` draws the blocks as selectable texts and says what a copy of each takes. The timeline's list is the one selection group around them, which is why this is not the kit's `Markdown`: that is a group of its own and a drag stopped at the end of a message.
- `src/tokens.rs`: includes the generated tokens and adds what is derived from them: the avatar tone an id hashes to; `MessageType`, every type style of a message's row and of the composer scaled to the font size chosen in Preferences (the views take a row's type from it, never from the plain tokens); the metrics and type styles the design canvas's boards draw that `tokens.json` names only in a usage line or not at all (a primary button's 48 points, an avatar's initials), each as arithmetic on tokens with the board's number beside it; and the code style, strong weight and syntax colours of a message body, which the design system does not name yet. A value a board uses that the tokens cannot make is a gap to report, not a literal for a view.
- `tests/body.rs`: message bodies through a windowless runtime (each construct, what stays as typed, links, selection across messages and what it copies, in both layouts). `benches/timeline.rs`: frame CPU of the message list over 1,000 varied messages, `cargo bench --features profile --bench timeline`, and `-- --minimal` for the same in one line; run it before and after a change to a row. The `bodies` scene draws every construct and a line per script with no instance (`--snap out.png --scene bodies --size 1180x2000`), and `blocks` a channel where people send several messages close together, with an edited message and a join line (`blocks-compact`, `blocks-minimal`, `blocks-avatars-hidden` and `blocks-font-20` the same with the Compact and Minimal presets, with avatars hidden and at the largest font size; `replies-minimal` the replies scene in one line; `preferences` the Preferences page, and `preferences-custom` with settings no preset matches; `server-settings` a server's settings, with a picture on the rail; `pictures` Grace's picture in her server DM's row, the member list and her messages; `members-over` the member list over a narrow window, at `--size 900x700`; `channels`, `channels-menu`, `browse`, `channel-preview`, `server-dm`, `add-people`, `new-dm`, `your-settings` and `person-in-server` being in channels and server DMs; `rail-folders`, `rail-menu`, `folder-menu` and `folder-settings` the rail's folders, a server's and a folder's menus and Folder settings; `replies`, `message-toolbar`, `message-menu`, `edit-message`, `delete-message`, `mention-list`, `emoji-picker` and `mentions` quote replies, editing and deleting, reactions, mentions and read state).
- `src/settings.rs`: the data directory (`LUMIA_DATA_DIR`, else `chat.lumia` under the platform's application-data directory) and `settings.json` (the instance to reopen, the channel last on screen, which a launch returns to, and what Preferences holds: appearance, the message settings and scroll bars, each read as its default alone when it is missing or not understood, so an older or newer file still reads). The message settings are `layout`, `spacing`, `avatars`, `font_size`, `images` and `embeds`; the presets (`Preset`: Comfortable, Compact, Minimal) are values that write them, never stored, and `Preset::matching` is the rule for which one the page shows. The stores under it follow `lumia-ffi`'s layout: `<host>/store.sqlite`, `<host>/keys.sqlite`, `identity/`.
- `tests/`: the screens through a windowless `rune::Runtime` with no instance, one file per part (`shell.rs`, `rail.rs`, `aside.rs`, `home.rs`, `servers.rs`, `channels.rs`, `replies.rs`, `server_settings.rs`, `account.rs`, `preferences.rs`, `links.rs`, `notices.rs`, `menu.rs`, `instance.rs`); `common/` is what they share (a state, the gestures, what an instance would report), and its `press` scrolls to its target first. `live*.rs` are the same shell against a real instance, with `lumia-cli` as the other people and devices: sending and a second launch from what was kept, history paged and scrolled back to a channel's first message, linking, personal conversations, the account screens, servers and invites, a server's settings reaching another member, who is typing between two shells, the browser handoff, a notification. Each skips itself without `LUMIA_DEV_INSTANCE` (and `LUMIA_CLI`, and for `live.rs` an account in `LUMIA_DEV_HANDLE` and `LUMIA_DEV_PASSWORD`).
- `scripts/smoke.sh`: seeds a dev instance with the release CLI and checks the debug shell against it: signed in, snapshot loaded, gateway connected, messages and members in the tree, a message typed into the composer reaching the instance, and then every test with the live tests' environment (only `live_app.rs`, which launches a real bundle and so takes the `lumia:` scheme on the Mac, is left to skip itself). It draws `out/smoke/shell.png` and `shell-dark.png` headlessly through Rune's `--snap`, which needs no window and no screen-recording permission; a scene from `src/scenes.rs` drawn the same way is how a change to a screen is looked at. `scripts/startup.py` times a launch to its first frame over a signed-in data directory (`cargo build --profile perf` first).
- `src/platform/`: what makes the shell an app around the window, and the only place that meets the system. `mod.rs` is the hooks `main` gives Rune (`on_open_url`, `on_focus`, the poll that pays what the state owes: pages to open, notices to post, the frame for AppKit to remember, the menu's items); its module comment says what each platform gets today and needs. `updates.rs` holds the updater (`lumia-sparkle`) on the main thread and is what the menu's two update items do; only a real launch of a bundle that names a feed has one. `system.rs` carries Preferences out where the system has a say (macOS: the app's appearance, and when scroll bars show), only in a real window. `instance.rs` is one running copy per data directory: a lock on `instance.lock` held for the process's life, and on Unix a socket a later launch hands its `lumia:` links to.
- `src/app/links.rs`, `notices.rs`, `menu.rs` with `src/session/browser.rs` and `notices.rs`: sign-in through the system browser and the `lumia:` link it returns on (every sign-in the shell starts carries a `state` the link must bring back; read the module comment before loosening it), the web page opened as this account, which message is owed a notification and what its click opens, and the menu bar's own items: the Account menu, the application menu's "Preferences…" (Command-comma, once signed in), and its "Check for updates…" and "Check for updates automatically" while there is an updater.
- `scripts/dist-linux.sh` and `scripts/dist-windows.sh` with `packaging/linux` and `packaging/windows`: the preview packages a release tag publishes for the other two desktops (a tarball and a `.deb`; a zip of `Lumia.exe` cross-built with MinGW-w64). Each script's head says what it checks and what it cannot; run them in a container before changing the release workflow's jobs.
- `scripts/bundle-macos.sh` with `packaging/macos/Info.plist`: makes `out/Lumia.app` (bundle identifier, version and build number, the `lumia:` scheme, the icon from the brand symbol, the update feed and its public key, `Sparkle.framework` from the release pinned at the script's head, a signature made inside out) and checks it. `scripts/dist-macos.sh VERSION` is the macOS release path: the disk image (`Lumia-<version>.dmg`, which a person downloads and an update installs from), signed, notarized and stapled when the Developer ID and the notary's credentials are in the environment, and the signed `appcast.xml`, with a delta from a previous release. Its signing and notarizing branch has not been run yet. `scripts/update-check.sh` proves the update end to end on this Mac under a scratch bundle identifier with throwaway keys: an installed build updating itself from a feed served locally, and the five releases it must refuse; run it after a change to the bridge, the bundle's update keys, the pin or either script. `tests/live_app.rs` launches a debug bundle for real (`LUMIA_DEV_APP`); `tests/live_browser.rs` and `tests/live_notice.rs` run the handoff and a personal message's notice against an instance with no window.

## Rules

- A link opened with the app, a later launch's arguments and a clicked notification's contents come from outside the app. They are parsed strictly and may only do what `State::open_url` and `State::open_notice` allow: complete a sign-in this app started, or show a conversation this account already has.
- A debug build's `LUMIA_DEV_BROWSER` and `LUMIA_DEV_TRACE` exist so a real launch can be checked with no hands on the window; a release build ignores them, as it ignores `LUMIA_DEV_INSTANCE`.

- Logic lives in the Rust core. A call a screen needs goes on `lumia_client::app::App` first; `session.rs` holds state and the views hold layout.
- Colours, distances, radii, shadows and type come from `tokens`; no literal values in views. Sentence case, typographic punctuation, no emoji in chrome.
- The screens mirror the web's (`apps/web/src/routes`) and the iOS app's (`apps/apple/Lumia-iOS`): the same states, wording and error handling.
- A screen is checked against its board by looking at both: draw the board (the design canvas's `.dc.html` in a browser at the board's size) and the shell (`--snap` at the same `--size`) and put the same region of each side by side. Reading the board's styles alone has passed over what a glance shows, such as a list anchored to the wrong end of its pane.
- Every interactive element has a role, a label, a focus ring and a key; a list is a `list` of `listitem`s. The accessibility tree is part of the screen (`--tree out.json` shows it).
- A message is text someone else wrote. Its links open only as `http` or `https`, and the shell fetches nothing a message names (no images, no previews). The one thing the shell does fetch that someone else chose is an avatar, and only from the instance it is signed in to, whose bytes the instance encoded itself (`session/avatars.rs`); a picture named on another host is not fetched.
- No `unwrap` or `expect` outside tests, and no `unsafe` (manifest lints); `crates/sparkle` is the exception for `unsafe` and says so in its manifest. What needs `unsafe` goes there, behind a safe function, not into the shell.
- The update feed is trusted through one key: `SUPublicEDKey` in the bundle, whose private half is never in the repository. The feed and every download are signed with it (`SURequireSignedFeed`, which needs `SUVerifyUpdateBeforeExtraction`); neither is to be turned off. Do not run Sparkle's `generate_keys`, which writes to the login Keychain. Moving the Sparkle pin means changing the version and the SHA-256 together and running `scripts/update-check.sh`.
- `cargo fmt`, `cargo clippy --all-targets -- -D warnings` and `cargo test` must pass, and `scripts/smoke.sh` against a dev instance after a change to a screen or the session.
- What the shell does not do yet is listed in plan step 9. Say so in the screen's module comment when a flow is missing, and do not draw a control for it.
