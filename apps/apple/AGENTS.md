This is Lumia on Apple platforms (architecture section 13): `LumiaKit`, the Swift package the macOS and iOS apps share, and one app directory per platform with its own layout. Read `../../docs/architecture.md` and `../../docs/plan.md` (step 7) before changing anything here.

## Layout

- `scripts/core.sh`: builds `lumia-ffi` for the Apple targets (`--ios` adds device and simulator; `--host` builds this machine's macOS slice only, which is what CI does), generates the Swift bindings with the workspace's `uniffi-bindgen`, assembles `LumiaKit/LumiaCore.xcframework`, and runs `scripts/tokens.py`, which writes `LumiaKit/Sources/LumiaKit/Tokens.swift` from `../../assets/design/tokens.json`. Everything it produces is ignored by git; run it before any build, with `DEVELOPER_DIR` pointing at Xcode.
- `LumiaKit/Sources/LumiaFFI`: the generated bindings (`LumiaFFI.swift`), a target of their own so their warnings stay out of ours.
- `LumiaKit/Sources/LumiaKit`: `LumiaClient` (an actor over the FFI `Client`; every call off the main thread, the listener as an `AsyncStream`), `LumiaSession` (`@Observable`, main actor: the snapshot, messages, DM channels and logs, the roster, the people, the connection state, kept fresh by the gateway's events the way the web's queries are), `AppStore` (the one session and the route: reopens the saved instance at launch, signs in from `LUMIA_DEV_*` in a debug build), `Design.swift` and the generated `Tokens.swift` (colours per appearance, spacing, radii, type styles), `Presentation.swift` (initials, the nine avatar tones, times) and `Components.swift` (avatar, notice, empty state, message row, request card, device row, composer, card, field, button styles).
- `Lumia-macOS`: the desktop app. `project.yml` is the XcodeGen definition (`xcodegen generate`; the project is not committed); `Sources` holds `LumiaApp` (the window and menus over the shared store), `SignInView`, `LinkView`, `ShellView` (the Quiet Split: rail, sidebar, main, aside; the channel view) and `HomeViews` (conversations, requests, new message, devices).
- `Lumia-iOS`: the phone app, the Quiet Split folded as the design canvas's iOS boards draw it: `Chrome.swift` (the rail, the sidebar header and tiles, `PanelScreen`: the floating panel a pushed screen draws itself in, with its own header since the system bar is hidden), `ShellView` (a `NavigationStack` whose root is the rail beside Home's conversations or a server's channels, every other screen pushed as a panel), `Screens.swift` (conversation, channel, requests, new message, devices with the revoke sheet), `SignInView` and `LinkView`. Same `project.yml` shape and bundle identifier as the macOS app; the simulator build is arm64 only (the core's simulator slice).
- `scripts/dist.sh <version> [--sign]`: the release build (architecture section 13, "Distribution"): a universal archive signed ad hoc, exported with Developer ID (`Lumia-macOS/ExportOptionsDeveloperID.plist`), with `--sign` notarized and stapled, on a DMG, and the Sparkle appcast when `SPARKLE_KEY_PATH` is set. Signing wants the Developer ID Application certificate in a keychain (the release workflow imports it from the `DEVELOPER_ID_P12` secret into a keychain of its own; this account's API keys are not offered cloud signing); notarization uses the App Store Connect API key (`ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_KEY_PATH`). The version is the tag; the build number is the commit count.
- Updates: the app embeds Sparkle; `SUFeedURL` and `SUPublicEDKey` come from the `LUMIA_UPDATE_FEED` and `LUMIA_UPDATE_KEY` settings in `project.yml`, so a fork points its builds at its own releases. The private key is a repository secret and never in the tree.
- `scripts/release.sh [--upload]`: the App Store archive and TestFlight upload (`Lumia-macOS/ExportOptions.plist`), kept for a store listing; not the release channel.
- `scripts/smoke.sh`: seeds a dev instance with the release CLI, launches the debug app signed in through the `LUMIA_DEV_*` environment (a debug build only), and checks the window and the gateway connection.
- `scripts/smoke-ios.sh`: the same for the iOS app in a simulator (`LUMIA_SIMULATOR` names it; any iPhone otherwise): installs the debug build, launches it once per screen with `LUMIA_DEV_SCREEN` (home, server, channel, requests, devices, new, signin, link) and screenshots each into `.build/smoke-ios/`, which is how a change to a screen is checked.

## Rules

- Logic lives in the Rust core; `LumiaKit` holds state and presentation, the apps hold layouts. A method a screen needs goes on `lumia_client::app::App` first, then through `lumia-ffi`.
- Colours, spacing, radii and type come from `LumiaTokens`; no literal values in views. Sentence case, typographic punctuation, no emoji in chrome.
- The screens mirror the web's (`apps/web/src/routes`): the same states, wording and error handling, so a change to one is a change to both.
- Build and test: `scripts/core.sh --ios`, then `swift test` in `LumiaKit`, `xcodebuild -project Lumia-macOS/Lumia.xcodeproj -scheme Lumia build` and `xcodebuild -project Lumia-iOS/Lumia.xcodeproj -scheme Lumia -destination 'generic/platform=iOS Simulator' -derivedDataPath Lumia-iOS/.build CODE_SIGNING_ALLOWED=NO build` (each after `xcodegen generate` in its directory). Run `scripts/smoke.sh` and `scripts/smoke-ios.sh` against a dev instance after a change to a screen or the session. `.github/workflows/macos.yml` runs all of that on a macOS runner, with the browser suite in WebKit on the same instance.
