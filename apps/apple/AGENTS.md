This is Lumia on iOS (architecture section 13): `LumiaKit`, the Swift package over the core, and `Lumia-iOS`, the app. The Mac app is not here: it is the desktop shell in `apps/desktop`, which replaced the SwiftUI macOS app that used to share this package (2026-11-11). Read `../../docs/architecture.md` and `../../docs/plan.md` (step 7) before changing anything here.

## Layout

- `scripts/core.sh`: builds `lumia-ffi` for the Apple targets (`--ios` adds device and simulator, `--ios-device` the device only; `--host` builds this machine's macOS slice only, which is what CI does), generates the Swift bindings with the workspace's `uniffi-bindgen`, assembles `LumiaKit/LumiaCore.xcframework`, and runs `scripts/tokens.py`, which writes `LumiaKit/Sources/LumiaKit/Tokens.swift` from `../../assets/design/tokens.json`. Everything it produces is ignored by git; run it before any build, with `DEVELOPER_DIR` pointing at Xcode.
- `LumiaKit/Sources/LumiaFFI`: the generated bindings (`LumiaFFI.swift`), a target of their own so their warnings stay out of ours.
- `LumiaKit/Sources/LumiaKit`: `LumiaClient` (an actor over the FFI `Client`; every call off the main thread, the listener as an `AsyncStream`), `LumiaSession` (`@Observable`, main actor: the snapshot, messages, DM channels and logs, the roster, the people, the connection state, presence by server from the gateway's diffs with `watchPresence` naming the servers on screen, and who is typing in the servers' channels: `typed(channelID:)` on every edit of a channel's composer that leaves something in it, `typingNames(in:)` for the line under it, an entry dropped by its author's message or by a wake the session sets for when it runs out; kept fresh by the gateway's events the way the web's queries are; a snapshot refused because the session is over, `lumiaSignedOut`, ends it as signing out does and leaves the sign-in screen its line, `takeEndedNotice()`, and a gateway loop that has ended asks for the snapshot), `AppStore` (the one session and the route: reopens the saved instance at launch, signs in from `LUMIA_DEV_*` in a debug build), `Design.swift` and the generated `Tokens.swift` (colours per appearance, spacing, radii, type styles), `Presentation.swift` (initials, the nine avatar tones, times), `Timeline.swift` (what a conversation's list is before it is drawn, as values the tests cover: `MessageBlocks`, the desktop shell's rule for which messages are one block, `dayLabel`, `TypingRoster`, `typingWords` and the dots' cycle) and `Components.swift` (avatar, notice, empty state, message row, day divider, request card, device row, composer with the typing line under it, card, field, button styles).
- `Lumia-iOS`: the phone app, the Quiet Split folded as the design canvas's iOS boards draw it: `Chrome.swift` (the rail, the sidebar header and tiles, `PanelScreen`: the floating panel a pushed screen draws itself in, with its own header since the system bar is hidden), `ShellView` (a `NavigationStack` whose root is the rail beside Home's conversations or a server's channels, every other screen pushed as a panel), `Screens.swift` (conversation and channel: messages in blocks, the avatar, name and time over the first and the rest under it with neither, each still one stop for VoiceOver that says whose it is and when, blocks 8 points apart, a divider over each day's first; under a channel's composer a line that is always there and names who is typing, never in a personal conversation, which sends and shows none; requests, new message, add a server: create one or join from an invite link or code with its preview first, new channel, invite people: a link with an expiry and a use limit to copy or share, over the server's invites with a revoke each, devices with the revoke sheet), `SignInView`, `LinkView` and `Push.swift` (APNs registration, the token to the instance as the `apns` subscription, and the notification centre delegate: a tapped notification's channel and kind, as the extension wrote them into the content, become `PushRegistrar.target`, which `ShellView` opens once the snapshot has the channel; a DM from Home, a mention in its server). Same `project.yml` shape and bundle identifier as the macOS app; the simulator build is arm64 only (the core's simulator slice).
- `Lumia-iOS/Notifications`: the notification service extension (architecture 15.5). The stores live in the app group `group.chat.lumia` (`AppStore.dataDirectory`), so the extension opens the same instance with `LumiaClient` and calls `notificationContent`, which the core runs under the exclusive single-writer lock (`lumia-client`'s `writer.rs`: the app holds it shared in the foreground and releases it in `background()`; the call lets go of its own client's shared hold for the duration, so the extension needs no `background()` first; `resume()` says whether the extension wrote, and the session restarts the gateway loop then). The push names only the instance's host; the app records each host's base URL in the group's `UserDefaults` for the extension's lookup. `UITests/` holds the UI tests the smokes drive, for what the simulator cannot do from the command line: answering the notification prompt, tapping a notification, and typing into a channel while reading the screen as assistive technology does.
- `scripts/release.sh [version] [--upload]`: the iOS archive and its upload to App Store Connect (`Lumia-iOS/ExportOptions.plist`), the phone's only channel; the release workflow runs it on a tag, after which the build is in TestFlight. Signing is automatic through the App Store Connect API key (the Apple Distribution certificate is cloud-managed; the App Store profiles are created on first use). Xcode 26.6 refuses the key for signing ("Authentication failed: Make sure a bearer token was provided") where 26.5 and 27 accept it, so the workflows name Xcode 26.5 on the runner; `ios-upload.yml` re-sends a build by hand with a version and an Xcode of choice. Exporting on this Mac needs the system rsync first on `PATH` (Homebrew's breaks Xcode's IPA step).
- `scripts/icon.py`: the iOS app icon, the brand symbol (`assets/brand/lumia-original-icon.png`) flattened onto the brand's dark ground, since App Store Connect refuses an icon with an alpha channel; its output is committed. The Mac app (`apps/desktop`) has the same bundle identifier and is not distributed through the store: the App Store Connect record `chat.lumia` carries the macOS platform (a platform cannot be removed once added) but no macOS version is submitted and its TestFlight builds are expired.
- `scripts/smoke-ios.sh`: seeds a dev instance with the release CLI and runs the iOS app in a simulator (`LUMIA_SIMULATOR` names it; any iPhone otherwise), signed in through the `LUMIA_DEV_*` environment (a debug build only): installs the debug build, launches it once per screen with `LUMIA_DEV_SCREEN` (home, server, channel, requests, devices, profile, new, add, newchannel, invite, signin, link) and screenshots each into `.build/smoke-ios/`, which is how a change to a screen is checked. The account is alone there, so its channel shows one block and nobody typing; `smoke-typing.sh` is the one with someone else in it.
- `scripts/smoke-typing.sh`: a server's channel with another person in it, who is the release CLI: they join the phone account's server, send three messages in a row, follow the channel, and type when asked. `testBlocksAndTypingInAChannel` checks that each of the block's three rows is one element that begins with their name and a time, that the line under the composer says they are typing, and that it empties by itself once they stop; it types into the composer, and the script checks that the other person was sent the phone's typing (one notice for a burst of keys). Screenshots in `.build/smoke-typing/`. It needs an instance that fans typing out (protocol 6.7), so one built from this tree, and is not in the macOS workflow yet.
- `scripts/smoke-push.sh`: the notification extension's path in a simulator: the phone is linked as a second device of a CLI identity (`LUMIA_DEV_LINK=1` exchanges the request and code through files in the data directory, the UI test answers the notification prompt), another CLI identity asks for a DM, the first CLI device accepts and the other sends, and a launch with `LUMIA_DEV_SCREEN=notify` stands in for the extension (the simulator's `simctl push` adds a notification directly and never launches a service extension): the same call under the same lock, its answer in `notification.txt`, checked for the message. Then the tap: a push with the rewritten content (the channel and kind) lands while a second UI test holds the app in the foreground, the test taps the banner and expects the conversation's panel. Last, for the eye and not as a check, three more messages are sent and the app is launched on the conversation (`LUMIA_DEV_SCREEN=conversation`, the account's first personal one) for `conversation.png`: a block of three under the other person's name and one of this account's. Needs `xcodebuild build-for-testing` signed to run locally (`CODE_SIGN_IDENTITY=- CODE_SIGNING_REQUIRED=NO`), since an unsigned build carries no app-group entitlement. The extension's launch itself is checked on a device.

## Rules

- Logic lives in the Rust core; `LumiaKit` holds state and presentation, the app holds layouts. A method a screen needs goes on `lumia_client::app::App` first, then through `lumia-ffi`.
- Colours, spacing, radii and type come from `LumiaTokens`; no literal values in views. Sentence case, typographic punctuation, no emoji in chrome.
- The screens mirror the web's (`apps/web/src/routes`): the same states, wording and error handling, so a change to one is a change to both.
- Build and test: `scripts/core.sh --ios`, then `swift test` in `LumiaKit` (on the Mac, which is why the package still builds for macOS; with `LUMIA_TEST_INSTANCE=http://localhost:4000` it also revokes a session on that instance and expects the session here to end, a test skipped without it and not set in the workflow yet) and `xcodebuild build-for-testing -project Lumia-iOS/Lumia.xcodeproj -scheme Lumia -destination 'generic/platform=iOS Simulator' -derivedDataPath Lumia-iOS/.build CODE_SIGN_IDENTITY=- CODE_SIGNING_REQUIRED=NO` (after `xcodegen generate` in `Lumia-iOS`). Run `scripts/smoke-ios.sh`, `scripts/smoke-typing.sh` and `scripts/smoke-push.sh` against a dev instance after a change to a screen, the session, or push. `.github/workflows/macos.yml` runs all of that but the typing smoke on a macOS runner, with the browser suite in WebKit on the same instance.
