This is Lumia on iOS (architecture section 13): `LumiaKit`, the Swift package over the core, and `Lumia-iOS`, the app. The Mac app is not here: it is the desktop shell in `apps/desktop`, which replaced the SwiftUI macOS app that used to share this package (2026-11-11). Read `../../docs/architecture.md` and `../../docs/plan.md` (step 7) before changing anything here.

## Layout

- `scripts/core.sh`: builds `lumia-ffi` for the Apple targets (`--ios` adds device and simulator, `--ios-device` the device only; `--host` builds this machine's macOS slice only, which is what CI does), generates the Swift bindings with the workspace's `uniffi-bindgen`, assembles `LumiaKit/LumiaCore.xcframework`, and runs `scripts/tokens.py`, which writes `LumiaKit/Sources/LumiaKit/Tokens.swift` from `../../assets/design/tokens.json`. Everything it produces is ignored by git; run it before any build, with `DEVELOPER_DIR` pointing at Xcode.
- `LumiaKit/Sources/LumiaFFI`: the generated bindings (`LumiaFFI.swift`), a target of their own so their warnings stay out of ours.
- `LumiaKit/Sources/LumiaKit`: `LumiaClient` (an actor over the FFI `Client`; every call off the main thread, the listener as an `AsyncStream`), `LumiaSession` (`@Observable`, main actor: the snapshot, messages, DM channels and logs, the roster, the people, the connection state, presence by server from the gateway's diffs with `watchPresence` naming the servers on screen, and who is typing in the servers' channels: `typed(channelID:)` on every edit of a channel's composer that leaves something in it, `typingNames(in:)` for the line under it, an entry dropped by its author's message or by a wake the session sets for when it runs out; kept fresh by the gateway's events the way the web's queries are; a snapshot refused because the session is over, `lumiaSignedOut`, ends it as signing out does and leaves the sign-in screen its line, `takeEndedNotice()`, and a gateway loop that has ended asks for the snapshot; a sign-in made while a session is held, which is what linking a phone that signed in with a password is, replaces that session in the core, and the gateway loop running on it comes back on the new one by itself, which a kit test checks against an instance; `identityClaim` signs in once, by the core's claim, and `load()` starts one loop however many ask at once; `signOut()`, the sign-out a person chooses: first, while the session can still say so, this phone's `apns` push subscription is taken back, since the instance keeps subscriptions by device and not by session, and a failure there stops nothing; then the gateway stops, the session is revoked, and the tokens and everything held of the account go, the identity and device keys staying; it leaves no line for the sign-in screen, and a second call or one while the session is already on its way out does nothing; `pushSubscribe(token:)` sends the phone's token once per value by `PushLedger`, a value the tests cover, which a failed send and a sign-out both empty, so the next sign-in subscribes again; the calls whose order this is go through `ask`, which a test replaces), `AppStore` (the one session and the route: reopens the saved instance at launch, signs in from `LUMIA_DEV_*` in a debug build, where `LUMIA_DEV_LINK=1` links the phone with the app already on screen and its gateway running on the password's session, as for someone who links from Devices; `signOut()` signs the session out and shows sign-in on the saved instance, with `signingOut` true meanwhile so a second tap does nothing), `Design.swift` and the generated `Tokens.swift` (colours per appearance, spacing, radii, type styles), `Presentation.swift` (initials, the nine avatar tones, times), `Timeline.swift` (what a conversation's list is before it is drawn, as values the tests cover: `MessageBlocks`, the desktop shell's rule for which messages are one block, `dayLabel`, `TypingRoster`, `typingWords` and the dots' cycle), `ServerSettings.swift` (what the Server settings screen decides before anything is sent, as values the tests cover: `ServerName`, 1 to 100 characters once trimmed and Save only for something that is not the name already; `Retention`, the choices Forever, 1 year, 90 days and 30 days with a value set elsewhere after them, and the warning when a choice is shorter than what the server keeps now, for ever the longest; `ServerSettingsRefusal`, the words for what the instance refuses, the Profile photo's for a picture; and `pictureURL`, which takes only the instance's own `/api/v1/avatars/` paths, as the core's `is_own_avatar` does; the session's `updateServer`, `setServerIcon` and `removeServerIcon` hold the snapshot each answers with), `Preferences.swift` (this phone's two choices, as values the tests cover: `Appearance`, light, dark or system, which is the default, and what it asks of the system; `Density`, comfortable, the default, or compact, and `MessageMeasures`, the message row's avatar and room at each, the desktop shell's `Measures` value for value; `Preferences`, `@Observable`, which reads them from `UserDefaults` at launch, anything not understood as the default, and writes each as it is made; they are not the account's, nothing sends them anywhere and signing out leaves them) and `Components.swift` (avatar, a picture the instance keeps drawn over what stands for it (`LumiaPictureOver`), notice, empty state, message row and day divider, each drawn by the `MessageMeasures` it is given, request card, device row, composer with the typing line under it, segmented tabs, which are also the design's choice of one among a few and say which is selected, card, field, button styles).
- `Lumia-iOS`: the phone app, the Quiet Split folded as the design canvas's iOS boards draw it: `LumiaApp.swift` (the routes, and the chosen appearance asked of the system for every screen, sign-in and linking included; while a sign-out is on its way it shows the launch's spinner and nothing of the account), `Chrome.swift` (the rail, which draws a server's picture over its initials when it has one, whose own avatar opens the account menu, the system's, in the web's and the desktop shell's order: View profile, Preferences, Devices, and under a rule Sign out, which the system draws as destructive and which asks nothing first; the sidebar header and tiles, `PanelScreen`: the floating panel a pushed screen draws itself in, with its own header since the system bar is hidden), `ShellView` (a `NavigationStack` whose root is the rail beside Home's conversations or a server's channels, every other screen pushed as a panel), `Screens.swift` (conversation and channel: messages in blocks, the avatar, name and time over the first and the rest under it with neither, each still one stop for VoiceOver that says whose it is and when, blocks 8 points apart, a divider over each day's first, or with the small avatar and half that room when Preferences says compact, which changes the list and nothing around it; under a channel's composer a line that is always there and names who is typing, never in a personal conversation, which sends and shows none; requests, new message, add a server: create one or join from an invite link or code with its preview first, new channel, invite people: a link with an expiry and a use limit to copy or share, over the server's invites with a revoke each, server settings: offered under a server's channels, after New channel and Invite people (the phone has no menu under the server's name), only when the snapshot says this account may change them (`canManage`), an Overview card with the server's picture, "Choose a picture…" through the system's photo picker and Remove, and the name with its Save, and a Message history card with the segmented choice, the warning in the error colour when the choice deletes messages, and its Save, profile, preferences: an Appearance card and a Messages card in the desktop page's words, no scroll bar card since a phone's indicators are the system's, and no board, so the Profile screen's cards with the segmented choice; devices with the revoke sheet), `SignInView`, `LinkView` and `Push.swift` (APNs registration, the token offered to the session at each appearance of the shell, each new token and each welcome, which sends it to the instance as the `apns` subscription once; when the account leaves the phone, signed out or sent back to sign-in, the app unregisters from APNs and forgets the token, so a subscription the instance could not be told to drop delivers nothing, and the next sign-in registers again, and it removes the notifications already delivered from Notification Center, all of them, since each names a conversation of the one account the phone held; the app schedules none of its own; a push that arrives in the foreground with no signed-in session, `PushRegistrar.signedIn`, is neither shown, listed nor sounded; and the notification centre delegate: a tapped notification's channel and kind, as the extension wrote them into the content, become `PushRegistrar.target`, which `ShellView` opens once the snapshot has the channel; a DM from Home, a mention in its server). Same `project.yml` shape and bundle identifier as the macOS app; the simulator build is arm64 only (the core's simulator slice).
- `Lumia-iOS/Notifications`: the notification service extension (architecture 15.5). The stores live in the app group `group.chat.lumia` (`AppStore.dataDirectory`), so the extension opens the same instance with `LumiaClient` and asks it `notice`, a `PushNotice` the kit's tests cover: nothing at all when the client is not signed in or the instance refuses its session (a subscription that outlived the session), the message when one could be read, else the generic notice. Nothing is handed to the system as empty content, which it drops only for an extension with the `com.apple.developer.usernotifications.filtering` entitlement; the extension does not have it (Apple grants it on request), so until then the generic notice is shown. The message comes from `notificationContent`, which the core runs under the exclusive single-writer lock (`lumia-client`'s `writer.rs`: the app holds it shared in the foreground and releases it in `background()`; the call lets go of its own client's shared hold for the duration, so the extension needs no `background()` first; `resume()` says whether the extension wrote, and the session restarts the gateway loop then). The push names only the instance's host; the app records each host's base URL in the group's `UserDefaults` for the extension's lookup. `UITests/` holds the UI tests the smokes drive, for what the simulator cannot do from the command line: answering the notification prompt, tapping a notification, typing into a channel, making a choice in Preferences, signing out from the account menu and pulling Notification Center down to read what it lists, while reading the screen as assistive technology does.
- `scripts/release.sh [version] [--upload]`: the iOS archive and its upload to App Store Connect (`Lumia-iOS/ExportOptions.plist`), the phone's only channel; the release workflow runs it on a tag, after which the build is in TestFlight. Signing is automatic through the App Store Connect API key (the Apple Distribution certificate is cloud-managed; the App Store profiles are created on first use). Xcode 26.6 refuses the key for signing ("Authentication failed: Make sure a bearer token was provided") where 26.5 and 27 accept it, so the workflows name Xcode 26.5 on the runner; `ios-upload.yml` re-sends a build by hand with a version and an Xcode of choice. Exporting on this Mac needs the system rsync first on `PATH` (Homebrew's breaks Xcode's IPA step).
- `scripts/icon.py`: the iOS app icon, the brand symbol (`assets/brand/lumia-original-icon.png`) flattened onto the brand's dark ground, since App Store Connect refuses an icon with an alpha channel; its output is committed. The Mac app (`apps/desktop`) has the same bundle identifier and is not distributed through the store: the App Store Connect record `chat.lumia` carries the macOS platform (a platform cannot be removed once added) but no macOS version is submitted and its TestFlight builds are expired.
- `scripts/smoke-ios.sh`: seeds a dev instance with the release CLI and runs the iOS app in a simulator (`LUMIA_SIMULATOR` names it; any iPhone otherwise), signed in through the `LUMIA_DEV_*` environment (a debug build only): installs the debug build, launches it once per screen with `LUMIA_DEV_SCREEN` (home, server, channel, requests, devices, profile, preferences, new, add, newchannel, invite, serversettings, signin, link) and screenshots each into `.build/smoke-ios/`, which is how a change to a screen is checked. A launch can also name Preferences' choices, `LUMIA_DEV_APPEARANCE` (light, dark, system) and `LUMIA_DEV_DENSITY` (comfortable, compact), which hold for that launch and are not stored; the smoke draws five more pictures with them: `preferences-dark`, `serversettings-dark`, `signin-dark`, `channel-compact` and `channel-compact-dark`. The account is alone there, so its channel shows one block and nobody typing; `smoke-typing.sh` is the one with someone else in it. Each smoke takes a CLI built elsewhere through `LUMIA_CLI` (a worktree has none of its own).
- `scripts/smoke-preferences.sh`: Preferences by hand. `testPreferencesAreChosenAndKept` opens the account menu on the rail's avatar and checks its three items and their order, goes to Preferences, checks its words and that each choice is a button inside a group named for what is chosen ("Appearance", "Message density") that says whether it is the one selected, System and Comfortable on a new phone; chooses Dark and Compact, launches again on the channel with neither named, finds both still chosen and chooses System and Comfortable back. The script checks by a pixel of each screenshot that the screen went dark as Dark was chosen, was dark at the next launch, and was the simulator's own appearance again once System was. Screenshots in `.build/smoke-preferences/`. Not in the macOS workflow yet.
- `scripts/smoke-server-settings.sh`: Server settings by hand. The phone signs in as a server's owner; `testServerSettingsAreChangedHere` opens Server settings from under the server's channels, checks its words, that the picture, the field ("Name") and the choices are labelled and Forever is the one selected, that both Saves are off while nothing has changed and for an empty name, renames the server with spaces around the new name, chooses 30 days, expects the warning before Save and none after; the script then reads the name back with the CLI's `servers` (trimmed) and the retention over HTTP (`GET /servers/{id}`, 30), gives the server a solid red picture with `lumia-cli server-update --icon`, and the test expects it on the screen (labelled "Server picture", with Remove) and says where the server's tile is on the rail, whose middle the script expects red in the screenshot. Then, on a new phone, `testServerSettingsAreNotOfferedToAMember` signs in as a member the owner invited and finds no Server settings. Choosing a picture through the photo picker is not driven. Screenshots in `.build/smoke-server-settings/`. About two minutes. Not in the macOS workflow yet.
- `scripts/smoke-signout.sh`: sign out by hand. `testSignOutFromTheAccountMenu` signs in from the environment, answers the notification prompt, opens the account menu light and dark and checks its four items, their order and that Sign out is a button by that name; taps it and expects the sign-in screen on the instance's host with no "You were signed out" line and no rail; signs in as a second account the script made by typing its handle and password into that screen, in the same run of the app, and expects that account's name on the rail, its server and channel, and nothing that names the first's; signs that one out; signs the first in again by hand; is then signed out from elsewhere, the script revoking its session over HTTP, and expects the sign-in screen with its line; and launches with no account named, which opens on sign-in. The test announces each step and waits for the script (`<step>.seen`), which asks the instance at each: each account's sessions over HTTP, signed in beside the phone as both (the phone's device has one session under the account it is signed in to and none under the other, none once it is out, and a different one after it signs in again), and, when `LUMIA_SMOKE_DB` names the instance's database, the phone's `relay_apns` subscription with `psql`, since no route lists subscriptions: there once the system has given the simulator a token (this Mac's simulator is given one; a runner's may not be, and the script says so and follows none), the signed-in account's, gone at each sign-out, and gone as the revocation from outside is answered, before the phone has heard of it, which is the instance's rule and not the phone's doing. The script also delivers a notification (`simctl push`) during each of the first account's two sign-ins; the test pulls Notification Center down and finds it listed, and not listed once the account has left, chosen or ended, having seen the sheet open both times; and one more while the phone is signed out with the app in the foreground on sign-in, which must be neither shown nor listed. It checks by a pixel that the menu was drawn light and dark and that the last launch is the simulator's own appearance. Last, `testSignOutWhenTheInstanceDoesNotAnswer`: the phone signs in through a listener of the script's that passes every byte on to the instance and then, told to, takes connections and answers nothing; Sign out is tapped, the rail must be gone within 5 seconds and the sign-in screen there within 45 (16 on this Mac: the core's 8 seconds for the unsubscribe and 8 for the sign-out), and the script finds the session still on the instance, which was never told, and ends it. Screenshots in `.build/smoke-signout/`. About four minutes. Not in the macOS workflow yet.
- `scripts/smoke-typing.sh`: a server's channel with another person in it, who is the release CLI: they join the phone account's server, send three messages in a row, follow the channel, and type when asked. `testBlocksAndTypingInAChannel` checks that each of the block's three rows is one element that begins with their name and a time, that the line under the composer says they are typing, and that it empties by itself once they stop; it types into the composer, and the script checks that the other person was sent the phone's typing (one notice for a burst of keys). Screenshots in `.build/smoke-typing/`. It needs an instance that fans typing out (protocol 6.7), so one built from this tree, and is not in the macOS workflow yet.
- `scripts/smoke-push.sh`: the notification extension's path in a simulator: the phone is linked as a second device of a CLI identity (`LUMIA_DEV_LINK=1` exchanges the request and code through files in the data directory, the UI test answers the notification prompt; the phone is in the app on the password's session while it waits, and afterwards the script finds, in the account's sessions over HTTP, one session of the phone's device that is not the password's, and the test that the phone is still in the app with the sidebar's line saying connected), another CLI identity asks for a DM, the first CLI device accepts and the other sends, and a launch with `LUMIA_DEV_SCREEN=notify` stands in for the extension (the simulator's `simctl push` adds a notification directly and never launches a service extension): the same call under the same lock, its answer in `notification.txt`, checked for the message. Then the tap: a push with the rewritten content (the channel and kind) lands while a second UI test holds the app in the foreground, the test taps the banner and expects the conversation's panel. Last, for the eye and not as a check, three more messages are sent and the app is launched on the conversation (`LUMIA_DEV_SCREEN=conversation`, the account's first personal one) for `conversation.png`: a block of three under the other person's name and one of this account's. Needs `xcodebuild build-for-testing` signed to run locally (`CODE_SIGN_IDENTITY=- CODE_SIGNING_REQUIRED=NO`), since an unsigned build carries no app-group entitlement. The extension's launch itself is checked on a device.

## Rules

- Logic lives in the Rust core; `LumiaKit` holds state and presentation, the app holds layouts. A method a screen needs goes on `lumia_client::app::App` first, then through `lumia-ffi`.
- Colours, spacing, radii and type come from `LumiaTokens`; no literal values in views. Sentence case, typographic punctuation, no emoji in chrome.
- The screens mirror the web's (`apps/web/src/routes`): the same states, wording and error handling, so a change to one is a change to both.
- Build and test: `scripts/core.sh --ios`, then `swift test` in `LumiaKit` (on the Mac, which is why the package still builds for macOS; with `LUMIA_TEST_INSTANCE=http://localhost:4000` it also revokes a session on that instance and expects the session here to end, signs one out and expects the instance to have lost it, and signs in over a held session twice, right after the gateway's welcome and eleven seconds into it, expecting one session on the instance each time and a message sent afterwards to come back through the gateway, and expects a push that arrives after the instance ended a session to be no notice; four tests skipped without it and not set in the workflow yet) and `xcodebuild build-for-testing -project Lumia-iOS/Lumia.xcodeproj -scheme Lumia -destination 'generic/platform=iOS Simulator' -derivedDataPath Lumia-iOS/.build CODE_SIGN_IDENTITY=- CODE_SIGNING_REQUIRED=NO` (after `xcodegen generate` in `Lumia-iOS`). Run `scripts/smoke-ios.sh`, `scripts/smoke-typing.sh`, `scripts/smoke-preferences.sh`, `scripts/smoke-signout.sh`, `scripts/smoke-server-settings.sh` and `scripts/smoke-push.sh` against a dev instance after a change to a screen, the session, or push. `.github/workflows/macos.yml` runs all of that but the typing, preferences, sign-out and server settings smokes on a macOS runner, with the browser suite in WebKit on the same instance.
