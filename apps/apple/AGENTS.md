This is Lumia on Apple platforms (architecture section 13): `LumiaKit`, the Swift package the macOS and iOS apps share, and one app directory per platform with its own layout. Read `../../docs/architecture.md` and `../../docs/plan.md` (step 7) before changing anything here.

## Layout

- `scripts/core.sh`: builds `lumia-ffi` for the Apple targets (`--ios` adds device and simulator, `--ios-device` the device only; `--host` builds this machine's macOS slice only, which is what CI does), generates the Swift bindings with the workspace's `uniffi-bindgen`, assembles `LumiaKit/LumiaCore.xcframework`, and runs `scripts/tokens.py`, which writes `LumiaKit/Sources/LumiaKit/Tokens.swift` from `../../assets/design/tokens.json`. Everything it produces is ignored by git; run it before any build, with `DEVELOPER_DIR` pointing at Xcode.
- `LumiaKit/Sources/LumiaFFI`: the generated bindings (`LumiaFFI.swift`), a target of their own so their warnings stay out of ours.
- `LumiaKit/Sources/LumiaKit`: `LumiaClient` (an actor over the FFI `Client`; every call off the main thread, the listener as an `AsyncStream`), `LumiaSession` (`@Observable`, main actor: the snapshot, messages, DM channels and logs, the roster, the people, the connection state, kept fresh by the gateway's events the way the web's queries are), `AppStore` (the one session and the route: reopens the saved instance at launch, signs in from `LUMIA_DEV_*` in a debug build), `Design.swift` and the generated `Tokens.swift` (colours per appearance, spacing, radii, type styles), `Presentation.swift` (initials, the nine avatar tones, times) and `Components.swift` (avatar, notice, empty state, message row, request card, device row, composer, card, field, button styles).
- `Lumia-macOS`: the desktop app. `project.yml` is the XcodeGen definition (`xcodegen generate`; the project is not committed); `Sources` holds `LumiaApp` (the window and menus over the shared store), `SignInView`, `LinkView`, `ShellView` (the Quiet Split: rail, sidebar, main, aside; the channel view) and `HomeViews` (conversations, requests, new message, devices).
- `Lumia-iOS`: the phone app, the Quiet Split folded as the design canvas's iOS boards draw it: `Chrome.swift` (the rail, the sidebar header and tiles, `PanelScreen`: the floating panel a pushed screen draws itself in, with its own header since the system bar is hidden), `ShellView` (a `NavigationStack` whose root is the rail beside Home's conversations or a server's channels, every other screen pushed as a panel), `Screens.swift` (conversation, channel, requests, new message, devices with the revoke sheet), `SignInView`, `LinkView` and `Push.swift` (APNs registration, the token to the instance as the `apns` subscription). Same `project.yml` shape and bundle identifier as the macOS app; the simulator build is arm64 only (the core's simulator slice).
- `Lumia-iOS/Notifications`: the notification service extension (architecture 15.5). The stores live in the app group `group.chat.lumia` (`AppStore.dataDirectory`), so the extension opens the same instance with `LumiaClient` and calls `notificationContent`, which the core runs under the exclusive single-writer lock (`lumia-client`'s `writer.rs`: the app holds it shared in the foreground and releases it in `background()`; `resume()` says whether the extension wrote, and the session restarts the gateway loop then). The push names only the instance's host; the app records each host's base URL in the group's `UserDefaults` for the extension's lookup. `UITests/` holds the one UI test the push smoke runs to answer the notification prompt.
- `scripts/dist.sh <version> [--sign]`: the release build (architecture section 13, "Distribution"): a universal archive signed ad hoc, exported with Developer ID (`Lumia-macOS/ExportOptionsDeveloperID.plist`), with `--sign` notarized and stapled, on a DMG, and the Sparkle appcast when `SPARKLE_KEY_PATH` is set. Signing wants the Developer ID Application certificate in a keychain (the release workflow imports it from the `DEVELOPER_ID_P12` secret into a keychain of its own; this account's API keys are not offered cloud signing); notarization uses the App Store Connect API key (`ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_KEY_PATH`). The version is the tag; the build number is the commit count.
- Updates: the app embeds Sparkle; `SUFeedURL` and `SUPublicEDKey` come from the `LUMIA_UPDATE_FEED` and `LUMIA_UPDATE_KEY` settings in `project.yml`, so a fork points its builds at its own releases. The private key is a repository secret and never in the tree.
- `scripts/release.sh [version] [--upload]`: the iOS archive and its upload to App Store Connect (`Lumia-iOS/ExportOptions.plist`), the phone's only channel; the release workflow runs it on a tag, after which the build is in TestFlight. Signing is automatic through the App Store Connect API key (the Apple Distribution certificate is cloud-managed; the App Store profiles are created on first use). Xcode 26.6 refuses the key for signing ("Authentication failed: Make sure a bearer token was provided") where 26.5 and 27 accept it, so the workflows name Xcode 26.5 on the runner; `ios-upload.yml` re-sends a build by hand with a version and an Xcode of choice. Exporting on this Mac needs the system rsync first on `PATH` (Homebrew's breaks Xcode's IPA step).
- `scripts/icon.py`: the iOS app icon, the brand symbol (`assets/brand/lumia-original-icon.png`) flattened onto the brand's dark ground, since App Store Connect refuses an icon with an alpha channel; its output is committed. The macOS icon keeps the transparent symbol. The macOS app is not distributed through the store: the App Store Connect record `chat.lumia` carries the macOS platform (a platform cannot be removed once added) but no macOS version is submitted and its TestFlight builds are expired.
- `scripts/smoke.sh`: seeds a dev instance with the release CLI, launches the debug app signed in through the `LUMIA_DEV_*` environment (a debug build only), and checks the window and the gateway connection. `LUMIA_DEV_SHOT=<png>` makes a debug build write its window to that file a few seconds after launch (`LUMIA_DEV_SHOT_AFTER` seconds; `LUMIA_DEV_PLACE=home` lands on Home), drawn from the view hierarchy, which needs no screen-recording permission; the smoke saves it as `.build/smoke/shell.png`, and that is how a change to the shell is checked against the design canvas's Quiet Split boards.
- `scripts/smoke-ios.sh`: the same for the iOS app in a simulator (`LUMIA_SIMULATOR` names it; any iPhone otherwise): installs the debug build, launches it once per screen with `LUMIA_DEV_SCREEN` (home, server, channel, requests, devices, new, signin, link) and screenshots each into `.build/smoke-ios/`, which is how a change to a screen is checked.
- `scripts/smoke-push.sh`: the notification extension's path in a simulator: the phone is linked as a second device of a CLI identity (`LUMIA_DEV_LINK=1` exchanges the request and code through files in the data directory, the UI test answers the notification prompt), another CLI identity asks for a DM, the first CLI device accepts and the other sends, and a launch with `LUMIA_DEV_SCREEN=notify` stands in for the extension (the simulator's `simctl push` adds a notification directly and never launches a service extension): the same call under the same lock, its answer in `notification.txt`, checked for the message. Needs `xcodebuild build-for-testing` signed to run locally (`CODE_SIGN_IDENTITY=- CODE_SIGNING_REQUIRED=NO`), since an unsigned build carries no app-group entitlement. The extension's launch itself is checked on a device.

## Rules

- Logic lives in the Rust core; `LumiaKit` holds state and presentation, the apps hold layouts. A method a screen needs goes on `lumia_client::app::App` first, then through `lumia-ffi`.
- Colours, spacing, radii and type come from `LumiaTokens`; no literal values in views. Sentence case, typographic punctuation, no emoji in chrome.
- The screens mirror the web's (`apps/web/src/routes`): the same states, wording and error handling, so a change to one is a change to both.
- Build and test: `scripts/core.sh --ios`, then `swift test` in `LumiaKit`, `xcodebuild -project Lumia-macOS/Lumia.xcodeproj -scheme Lumia build` and `xcodebuild build-for-testing -project Lumia-iOS/Lumia.xcodeproj -scheme Lumia -destination 'generic/platform=iOS Simulator' -derivedDataPath Lumia-iOS/.build CODE_SIGN_IDENTITY=- CODE_SIGNING_REQUIRED=NO` (each after `xcodegen generate` in its directory). Run `scripts/smoke.sh`, `scripts/smoke-ios.sh` and `scripts/smoke-push.sh` against a dev instance after a change to a screen, the session, or push. `.github/workflows/macos.yml` runs all of that on a macOS runner, with the browser suite in WebKit on the same instance.
